# Ритуалы Habitify

Ритуал — группа привычек, которые выполняются подряд в определённое время дня. В Habitify это Область, выбранная пользователем как ритуал. Её `areaId` хранится во встроенной памяти хоста как настройка по [setup.md](setup.md), без служебных пометок в названии. Состав берётся из актуальных связей Habitify, отметки остаются у отдельных привычек. Порядок пользователь держит ручной сортировкой в приложении. Сон не ритуал.

Для записей действуют [operation-policy.md](operation-policy.md), [habitify-tools.md](habitify-tools.md) и [safety.md](safety.md). Явную полную команду или группу выполняй сразу без Preview; одиночное предложение агента — одна строка + «да», набор, собранный агентом, — один Preview. Запись → Read-back последовательно, стоп на первой ошибке, отказе хоста или `unverified`, отчёт `applied` / `unverified` / `unapplied`, без автоматического повтора и отката. Фон только читает, включая настройки памяти.

## Найти ритуал и его состав

Используй выбранный `areaId` из запроса или настройки памяти, прочитай `get-area`. При поиске по названию дочитай `list-areas`; похожее имя не выбирает объект. Если память недоступна, используй явно выбранную область в текущем разговоре по setup.md, без файлового fallback и обещания сохранения.

Для состава дочитай все страницы `list-habits` с этим `areaId`, отдельно активные и архивные, затем адресные `get-habit`. Проверь принадлежность и полноту по habitify-tools.md. Не считай порядок ответа порядком ритуала. Не исключай архивные привычки молча; покажи их отдельно, если они входят в состав. Неполный список не позволяет утверждать «все» или выполнять массовую отметку. Если архивному звену недоступна запись, останови зависимую группу до первой записи и назови ограничение; не восстанавливай его автоматически.

Используй известные данные. Неоднозначный ритуал, неуказанный состав для сборки и остальные блокирующие пробелы собери одним сообщением; цвет, иконку и необязательные настройки не спрашивай. При глубоком уточнении намерения используй `grill-me`; если он недоступен, назови его и рекомендуй установить средствами хоста.

## Собрать, добавить, убрать

**Собрать из существующих привычек.** Найди явно выбранные привычки и область. Если нужна новая область, создай её и прочитай `get-area`, затем назначай её выбранным привычкам по [areas.md](areas.md). Используй ID из ответа создания, не предполагаемый ID. В существующей области не снимай другие связи молча: её текущие участники также станут составом ритуала. После успешного назначения сохрани выбранный `areaId` как настройку ритуала и прочитай настройку обратно. Если запись памяти не подтверждена, сообщи об этом отдельно от уже применённых назначений. Пользователь вручную выставляет порядок в приложении; API его не записывает и не проверяет.

**Добавить звено.** Назначь область существующей выбранной привычке с сохранением остальных связей по areas.md. Если это новое поведение, используй [experiments.md](experiments.md): правило одного эксперимента и Safety сохраняются, группировка не разрешает новые эксперименты автоматически. Место звена в порядке пользователь меняет в приложении.

**Убрать звено.** Сними только связь выбранной привычки с областью ритуала по areas.md. Не удаляй и не архивируй привычку, её историю, план или остальные связи. Если убирается известная первая привычка, сними её `habitId` из настройки ритуала по setup.md, не назначай другую первой и не переноси напоминание скрыто: при необходимости старта нужен выбор первой привычки по имени или ID через поиск habitify-tools.md. Существующие напоминания сами от снятия связи не исчезают; явно сообщи об этом.

Для каждого `update-habit` восстанови всю writable-конфигурацию по habitify-tools.md и проверь её целиком после записи. Полный `areaIds` заменяет набор связей; сохрани прочие назначения, цели, расписание и напоминания. При неполных данных или неоднозначном преобразовании остановись до записи и предложи ручное изменение в приложении.

## Старт и напоминания

Время старта — выбранное напоминание `reminders.timeTriggers` первой привычки. API не даёт поля порядка и не определяет первую привычку, поэтому её `habitId` хранится настройкой ритуала рядом с `areaId` (setup.md). Если пользователь назвал первую привычку, разреши название штатным поиском по habitify-tools.md, сохрани её как настройку и перечитай; известный `habitId` не спрашивай повторно. Если первая привычка неизвестна и запрос меняет старт, уточни только её выбор вместе с другими блокирующими пробелами, не угадывай по списку или времени. Для сборки, чтения отметок и показа ритуала первая привычка не обязательна: без неё скажи «время старта не установлено», без вопроса. Порядок остальных привычек в памяти не храни. Поле `startDate` — не время старта ритуала; Time of Day — временной фильтр. Длительности ритуала в Habitify нет.

Перед изменением прочитай первую привычку. В `timeTriggers` задай выбранное время и сохрани остальные triggers, дни, параметры и виды напоминаний вместе со всей writable-конфигурацией. Если triggers несколько и непонятно, какой менять, или timezone/дни не установлены и нужны для запроса, уточни эти блокирующие данные одним сообщением. Точные аргументы бери из inputSchema хоста. При несовместимости response/request не обходи guard частичным PUT — предложи ручную настройку. После записи прочитай `get-habit`; Read-back подтверждает конфигурацию, не доставку уведомления.

Если пользователь ведёт блок Распорядка этого ритуала в календаре и просит сдвиг старта, той же командой передай изменение блока `jedikit-calendar`: фактически загрузи его `SKILL.md` и правила записи, затем выполни по ним. До первой записи проверь доступность обоих этапов, найди блок Распорядка и собери все блокирующие пробелы обоих этапов одним сообщением. Если режим серии не назван, передай `thisAndFollowing` с ближайшего будущего вхождения: прошлое не меняется. Затем Habitify → Read-back → календарь по правилам владельца, стоп на первой ошибке, без отката. Полная явная команда не требует отдельного подтверждения передачи. Если `jedikit-calendar` недоступен, явно скажи «блок Распорядка не изменён»; не объявляй передачу состоявшейся. При доступном изменении Habitify отчитай его отдельно. Сдвиг календаря сам по себе не меняет напоминание Habitify.

`reminders.habitStacks` меняй **только по просьбе пользователя**. Предупреди: переход запускается после отметки статуса, а не физического действия; пропуск или неотмеченная привычка может разорвать цепочку напоминаний. Это правила уведомлений, не порядок списка и не выполнение ритуала. При полной явной просьбе предупреждение не добавляет отдельного подтверждения.

Для stacks нужны выбранные исходная и целевая привычки, условие статуса и время перехода. Используй `conditionHabitId`, `type`, `timerType`, при `after` — выбранный `timerDelaySecs` по схеме хоста. Не подставляй `skipped`, `failed` или `reminder` как запасной переход без запроса. Проверь затрагиваемые входящие/исходящие зависимости, включая внешние привычки; не создавай ветви или циклы скрыто. Сохрани остальные stacks и reminders через полный PUT guard. Сборка, добавление или снятие звена сами по себе не разрешают перенастройку stacks; если для запрошенного изменения не хватает полноты зависимостей, остановись до записи и предложи ручную настройку.

## Статус и массовая отметка

«Как утренний ритуал?» и «Ритуал выполнен?» — чтение за выбранную дату в timezone пользователя по habitify-tools.md. Для каждой привычки прочитай адресный статус/отметки; Journal может помочь обзору, но не заменяет адресную проверку. Покажи итог вроде «Утренний ритуал: 7 из 10 отмечены выполненными; не отмечены выполненными: вода, растяжка, зарядка», различая `failed`, `skipped` и отсутствие данных. Вердикт «выполнен» допустим только при полном составе и отметке выполнения у всех; неизвестное, пустая область и отсутствие данных не дают такого вердикта. Дневные статусы не доказывают порядок, выполнение подряд или длительность.

«Ритуал выполнен» и «сделал утренний ритуал» — явная команда массово отметить все привычки выбранного ритуала за дату. После установления полного состава и исходных данных даты выполняй адресные отметки по [tracking.md](tracking.md), без Preview, последовательно с Read-back. Не отмечай чужие области, не создавай привычки или неизвестные количества, не подменяй безопасный критерий вредным эпизодом. Уже подтверждённые выполненными звенья не дублируй; покажи их отдельно. Если требуется количество, единица или безопасная трактовка и они неизвестны, собери все блокирующие пробелы до первой записи. Для отмены отметок остаётся однострочное подтверждение потерь.

## Обзор ритуала

Прочитай актуальный состав, доступную конфигурацию и индивидуальные отметки за запрошенный период; без периода начни с текущего дня. Покажи выполненное, пропуски и неизвестное отдельно. Спроси только о неизвестном, необходимом для запрошенного решения; при запросе улучшений оцени доступную нагрузку и потерянные переходы, не выдавая догадки за данные. Предложи одно изменение; набор изменений агента требует одного Preview.

В исследовании Keller 2021 не выявлено различий между сигналом по часам и сигналом-рутиной; это не доказывает их равенство для любого человека. Не обещай научное преимущество одного сигнала, оптимальное число звеньев или пользу длинного ритуала как целого. Один пропуск не обнуляет формирование отдельного поведения; этот вывод не доказывает устойчивость всей цепочки. Для нового поведения сохраняй рамку одного эксперимента; клинические риски веди по safety.md.

Для сопровождающих: исследовательская база — `research/habits/rituals.md`.
