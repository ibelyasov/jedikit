# Операции

Назначение: выполнить setup, capture, triage и минимальную проверку проекта без скрытой миграции или импровизированных workflow.

## Разделы

1. Общий протокол записи
2. Setup
3. Capture
4. Triage
5. Project
6. Внешние системы

## 1. Общий протокол записи

Перед workflow проверь нужные tools по [MCP-контракту](mcp-contract.md).

```text
одна явная обратимая запись
→ выполнить → прочитать результат обратно → сообщить

предложенная агентом запись или 2+ writes
→ полный preview → одно явное подтверждение
→ последовательные writes → read-back → ledger

первая ошибка
→ остановка → applied / error / unapplied → без rollback
```

Не считать «давай обсудим», «хочу» или ответ на уточнение подтверждением скрытого плана. Подтверждение должно следовать после preview и однозначно относиться ко всему показанному набору.

## 2. Setup

1. Проверь capabilities и выполни read-only `project_list`, затем прочитай существующие задачи только для подсчёта и списка кандидатов вне выбранной иерархии.
2. Покажи найденную иерархию, количество старых задач и кандидатов на последующий разбор. Не перестраивай существующие проекты и не меняй задачи.
3. Рекомендуй переиспользовать или создать root-контейнеры `Работа`, `Личное`, а внутри каждого — `Общее` для одиночных задач без реального проекта. Пользователь может выбрать дополнительные roots.
4. Собери по одному вопросу за turn: timezone; рабочие дни; окна daily open/close и weekly; режим каждого дополнительного root (`рабочие дни / личные дни / всегда`).
5. Покажи единый preview только отсутствующих контейнеров и настроек. Миграция существующих сущностей в этот preview не входит.
6. После подтверждения создавай проекты последовательно: roots через `project_create(title)`, дочерние `Общее` через `project_create(title,parent)`.
7. Прочитай созданные проекты обратно и сохрани в native memory только IDs/modes, timezone, рабочие дни и окна обзоров. Итог покажи в ответе; служебную задачу, проект или заметку конфигурации не создавай.

Root areas и `Общее` — контейнеры: не требуй у них результата и следующего шага. Setup остаётся read-only для старых задач/проектов. Если пользователь позднее отдельно запускает миграцию, сначала заново прочитай выбранные кандидаты, получи решение по каждому, покажи собственный полный preview и запроси подтверждение; не считай подтверждение setup разрешением на миграцию. При совпадающих названиях уточни по иерархии/ID, не создавай дубликат.

## 3. Capture

Явное «запиши/сохрани, чтобы не забыть» означает одну обратимую запись:

1. Возьми исходную пользовательскую фразу без улучшения.
2. Создай один Inbox item через `task_create(title)` без `projectId`, `start`, `deadline`, priority и metadata.
3. Прочитай item обратно и скажи, что это временное входящее до triage.

Не применяй capture к обычному вопросу, справочному ответу или фразе без просьбы сохранить.

## 4. Triage

Обрабатывай строго один item:

1. `task_list_inbox`, затем `task_get(id)` выбранного item.
2. Определи `task / project / idea / reference / meeting` по [ядру](core-method.md).
3. Предложи финальный title, destination и только обоснованные поля. Задай один вопрос с рекомендацией, если тип/destination неоднозначны.
4. Покажи preview. До подтверждения writes = 0.
5. Для задачи выполни `task_update(id,title,...)`, затем при необходимости `task_move(id,projectId)`.
6. Для проекта одним preview предложи `project_create`, затем `task_update` исходного item до ближайшего шага и `task_move` в новый проект. Не вызывай `task_create` для этого шага. Если пользователь пока не может назвать шаг, используй после его подтверждения конкретную задачу `Определить следующий шаг для проекта <название>`.
7. Для задачи или проекта после подтверждения raw title заменён в том же item. Не сохраняй raw в note, history, tag или metadata.

Idea/reference/meeting:

1. Спроси выбранное место; для meeting назови календарную границу.
2. Дай конкретную инструкцию ручного переноса. Не создавай дубликат, prep или follow-up task.
3. Дождись отдельного сообщения пользователя, что перенос завершён. Инструкция или согласие перенести не равны подтверждению завершения.
4. Проверь подтверждённую схему permanent-delete tool. Текущий hosted contract её не публикует: объясни capability gap, оставь item без изменений и не подменяй delete архивом/cancel.
5. Если будущий подтверждённый контракт предоставит delete, покажи отдельный preview с ID/title ровно одного исходного item, запроси второе подтверждение именно удаления, удали и проверь отсутствие item.

## 5. Project

Для проверки реального проекта:

1. `project_get(id)` и `task_list(projectId)`; контейнер остановить с пояснением.
2. Коротко назвать ожидаемый результат из title/note, открытые задачи, явные блокеры и наличие стартуемого шага.
3. Если результата или шага нет, задать один вопрос и предложить вариант; не записывать без подтверждения. Если пользователь выбирает оставить проект активным без известного шага, предложить конкретную задачу `Определить следующий шаг для проекта <название>`.
4. При отказе от активного проекта обязательно запросить короткую причину. До её получения ничего не архивировать; причину добавить в видимую note/history проекта, не перезаписывая существующий полезный context.
5. Каждую открытую задачу разобрать отдельно: `перенести / отменить / оставить проект активным`. Только после решений по всем задачам показать единый точный preview: запись причины, перемещения/отмены и архив проекта.
6. После подтверждения выполнить операции последовательно, затем `project_archive(id)` и проверить результат. Массовую отмену по умолчанию и permanent delete не использовать.

Завершение отдельной задачи не запускает project check и не создаёт новый шаг автоматически.

## 6. Внешние системы

Jira, CRM, email и другие рабочие системы остаются источником истины для своих объектов. В SingularityApp сохраняй только личное ближайшее действие и разрешённую ссылку/context. Не копируй статусы, историю и чужие обязательства и не меняй внешнюю систему.

Применяй к локальному действию правила формулировки задачи: физический глагол, объект и наблюдаемый результат. Если пользователь назвал только внешний результат, ничего не записывай и задай один вопрос с конкретной рекомендацией, например: «Рекомендую “Открыть Jira и выписать ближайший шаг подготовки релиза”. Сохранить это действие во Inbox?»

Permanent delete вне описанного cleanup-контракта, true batch, delayed/background writes, server prompts и backlog workflows не поддерживаются. Пока MCP-контракт не подтверждает delete-tool, cleanup также fail closed. Если сценария здесь нет, остановись и объясни границу.
