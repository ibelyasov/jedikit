# Контракт инструментов SingularityApp

Операции SingularityApp даёт официальный hosted SingularityApp MCP, подключённый в Hermes как сервер `singularity`. Ожидаемый набор задан в [tools.json](../tools.json) (загрузка — `skill_view(name="<имя этого скилла>", file_path="tools.json")`): `server` — `singularity`, `name` — базовое имя, `access` — `read` или `write`.

## Вызов в Hermes

- Callable name — `mcp__singularity__<name>`; любой символ вне `[A-Za-z0-9_]` заменяется на `_`. Пример: `task_list_inbox` → `mcp__singularity__task_list_inbox`. Вызывай только имя, у которого часть после `mcp__singularity__` совпадает с базовым именем.
- Если нужный MCP-инструмент виден напрямую, вызывай его по callable name. Иначе schemas отложены Tool Search, и отсутствие инструмента в видимом списке не значит, что его нет: найди нужные `tool_search(queries=[…])`, получи schemas группой `tool_describe(names=[…])`, вызывай `tool_call(calls=[{name, arguments}])` — один MCP-вызов в `calls` за раз. Если точное имя уже известно, начни с `tool_describe`.

## Approval Hermes

Сервер `singularity` подключён с `trust=untrusted`: на вызов без `readOnlyHint` Hermes сам спрашивает approval, иногда и на чтение. Это допуск вызова Hermes, а не согласие по [правилам записи](write-policy.md#разрешение): одно не заменяет другое. Сначала нужное согласие пользователя, затем вызов; approval скилл не настраивает и не обходит.

- Отказ approval записи — этот вызов `unapplied` с причиной «Hermes не разрешил вызов»; группа остановлена, остаток `unapplied`, подтверждённые Read-back записи остаются `applied`.
- Отказ approval Read-back — результат записи `unverified`.
- Повтор — только по новой просьбе пользователя.

## Инструменты

| Возможность | access | Базовые имена |
| --- | --- | --- |
| Контекст аккаунта, только если нужен в области запроса | read | `get_my_context` |
| Чтение задач | read | `task_get`, `task_list`, `task_list_inbox`, `task_list_today`, `task_list_overdue` |
| Создание задачи | write | `task_create` |
| Поля и место задачи | write | `task_update`, `task_move` |
| Состояние задачи | write | `task_complete`, `task_complete_today`, `task_uncomplete`, `task_cancel`, `task_archive`, `task_unarchive` |
| Чтение проектов и дерева | read | `project_get`, `project_list` |
| Проекты | write | `project_create`, `project_update`, `project_archive`, `project_unarchive` |
| Чтение Разделов | read | `task_group_get`, `task_group_list` |
| Разделы | write | `task_group_create`, `task_group_update` |
| Чтение Тегов | read | `tag_get`, `tag_list` |
| Теги | write | `tag_create`, `tag_update` |
| Чтение Чек-листа | read | `checklist_item_get`, `checklist_item_list` |
| Чек-лист | write | `checklist_item_create`, `checklist_item_update`, `checklist_item_check`, `checklist_item_uncheck` |

Удаления и batch в контракте нет. Не вызывай `habit_*`, `habit_progress_*`, `kanban_status_*`, `task_change_column`, `time_stat_*`, даже если Tool Search их находит: видимость лишних инструментов не расширяет сценарии.

## Проверка перед сценарием

1. Найди нужные сценарию инструменты в видимом списке или через `tool_search` и сопоставь с базовыми именами. Весь каталог для Capture не требуй. `get_my_context` — чтение данных аккаунта, а не проверка возможностей: не вызывай его как обязательный preflight.
2. В schema инструмента (видимой или из `tool_describe`) проверь required fields, типы и только используемые поля: ID, текст, проект или Раздел, заметку, дату, состояние, связи Тегов. Особенности формата дат, снятия даты, связи Раздела с проектом проверяй, когда сценарий их использует.
3. ID и назначение бери из текущих list/get. Явно названный ID не требует повторного выбора по названию. Если кандидатов несколько, покажи пути и ID среди блокирующих пробелов.
4. Для Группы операций заранее проверь инструменты, поля и Read-back всех этапов. ID созданного объекта бери из проверенного ответа, не придумывай.
5. REST signatures, фильтры и форматы из UI в MCP не переноси.

## Поля и значения

- `deadline` — Срок, `start` — Плановая дата. Дату вычисляй в известном timezone пользователя от текущей даты в нём; спрашивай пояс, только если он нужен и неизвестен.
- `priority` — integer: `0 = HIGH`, `1 = NORMAL`, `2 = LOW`.
- `checked` пункта Чек-листа — integer: `0 = EMPTY`, `1 = CHECKED`, `2 = CANCELLED`. Строки enum не передавай; семантику выполнения задачи из этого enum не выводи.
- Длительность — поле, которое schema инструмента даёт для оценки времени (`timeLength`); единицу проверяй по schema.

## Чтение списков

Проверь продолжение и признаки полноты ответа и дочитай страницы в выбранной области. Если ответ неполон или формат продолжения неизвестен, явно ограничь вывод. Одна неполная страница не доказывает отсутствие задачи, пустоту или охват «всех проектов». Закрытие проекта не начинай без полного списка его открытых задач.

## Read-back

- Capture: прочитай созданный объект и подтверди, что он во Inbox; если get этого не показывает, используй `task_list_inbox`, проверив это чтение до записи.
- Перенос: тот же ID в новом месте.
- `task_cancel`, `task_archive`, `project_archive`: чтение, которое показывает это состояние, по текущей семантике инструмента, без догадок о поле или enum. Исчезновение из активного списка само по себе состояние не подтверждает.

## Нет инструмента

Если нет нужного инструмента, поля или понятной семантики, скажи: «Не могу выполнить <сценарий>: в текущем MCP нет <имя/поле>. <Что прочитано и что осталось без изменения>». Останови зависимую часть, независимую продолжай. Не расширяй scopes, не переходи на REST, не изобретай поле.

Назови недостающие базовые имена и рекомендуй подключить официальный hosted SingularityApp MCP `https://mcp.singularity-app.com/mcp` в Hermes сервером `singularity`. После настройки заново найди инструменты и schemas. JediKit не объявляет MCP; OAuth, установку и конфигурацию выполняет пользователь в Hermes, агент их не меняет. Наличие инструмента не доказывает рабочую авторизацию.
