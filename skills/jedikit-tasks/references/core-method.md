# Ядро метода

Назначение: классифицировать входящее и сформулировать задачу или минимальный проектный контур. Если сценария ниже нет, остановиться и не придумывать правило.

## Разделы

1. Классификация
2. Формулировка задачи
3. Проект и ближайший шаг
4. Даты и оценки
5. Неоднозначность и перегруз

## 1. Классификация

Сначала спроси: что пользователь хочет получить и требует ли это больше одного действия?

| Тип     | Признак                                                  | Действие v1                                                                         |
| ------- | -------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| Задача  | одно физически выполнимое действие с видимым результатом | предложить ясный title и подходящий реальный проект/`Общее`                         |
| Проект  | желаемый результат требует нескольких действий           | зафиксировать результат и ровно один стартуемый ближайший шаг                       |
| Идея    | возможность без принятого обязательства                  | объяснить тип и предложить выбранное пользователем место; своего инкубатора нет     |
| Справка | материал нужен для чтения/поиска, а не выполнения        | предложить выбранное пользователем место; не превращать в задачу без действия       |
| Встреча | событие в конкретный момент                              | направить в календарь; интеграции нет, можно отдельно оформить подготовку/follow-up |

Если тип меняет destination или создаваемые сущности, задай ровно один вопрос с рекомендацией. Пример: «Это похоже на идею, а не обязательство. Рекомендую сохранить её в вашем списке идей — куда вы его ведёте?»

## 2. Формулировка задачи

Хороший title отвечает на три вопроса:

- что физически сделать;
- с каким объектом/человеком;
- по чему понятно, что закончено.

Используй глагол, который можно начать без дополнительного обдумывания. Полезный context, ссылка и условия идут в note только если реально помогают выполнить действие.

| Слабо                  | Лучше                                                                             |
| ---------------------- | --------------------------------------------------------------------------------- |
| `Подарок маме`         | `Выбрать подарок маме и сохранить ссылку на выбранный вариант`                    |
| `Отчёт`                | `Отправить Анне отчёт за июль и получить подтверждение доставки`                  |
| `Разобраться с сайтом` | `Открыть аналитику сайта и выписать три страницы с максимальным падением трафика` |

Не сохраняй исходную формулировку рядом с подтверждённой новой: после triage остаётся только актуальный title и полезный context.

## 3. Проект и ближайший шаг

Проект описывает наблюдаемый результат, а не тему деятельности. Ближайший шаг должен быть физическим, стартуемым сейчас и продвигать результат.

Пример:

- результат: `Личный сайт опубликован на выбранном домене`;
- ближайший шаг: `Выписать обязательные разделы первой версии сайта`.

Не создавай список будущих шагов «для полноты». Когда задача завершена, новый шаг появляется только по желанию пользователя либо при daily/weekly review. Контейнеры root/`Общее` не являются реальными проектами и не требуют результата/шага.

## 4. Даты и оценки

- `deadline`: внешнее обязательство или событие, после которого результат теряет смысл/возникают последствия.
- `start`: выбранная пользователем дата, когда задача должна попасть в фокус.
- Без основания оставляй оба поля пустыми.
- Просроченный `start` означает лишь несверенный план; не называй это нарушенным сроком.
- Не переноси `start` молча. Для исключённых из Today задач предложи `оставить / снять start / выбрать новую дату`.
- Не меняй deadline, priority или `timeLength` по догадке. Значения `HIGH/NORMAL/LOW` и длительность выбирает пользователь.

## 5. Неоднозначность и перегруз

Существенная неоднозначность — та, что меняет тип, destination, дату или side effect. Задай один вопрос, назови рекомендуемый вариант и жди ответа. Не задавай пакет вопросов.

При перегрузе не вводи магический лимит задач. Назови наблюдаемый риск и предложи один подходящий путь:

- для необязательного — сократить результат, снять `start` или отказаться;
- для личного обязательства — отменить только после явного решения пользователя;
- для обещания другому человеку — предложить пересогласовать объём или срок, не меняя `deadline` молча.

Делегирование, waiting и отдельный процесс ожиданий находятся вне v1. Решение всегда остаётся пользователю. Опциональный быстрый шаг допустим только после его выбора и не отменяет triage/review.
