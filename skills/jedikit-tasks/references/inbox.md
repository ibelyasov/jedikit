# Capture и Triage

Записи — по [правилам записи](write-policy.md).

## Возможности сценария

Для Capture нужны создание задачи во Inbox и чтение созданной записи. Для Triage — чтение Inbox, выбранной задачи и дерева, изменение текста и места задачи с сохранением ID. Для нового проекта дополнительно нужны создание проекта с назначением родителя и чтение результата; для отказа или перенесённых записей — `task_cancel` и чтение состояния задачи. Даты, приоритет, длительность и полезный текст изменяй только когда они выбраны для сценария.

## Capture: запиши сразу

1. На явную просьбу «запиши», «сохрани во Inbox» или равнозначную команду возьми текст как есть, без Triage и требования чистовой формулировки.
2. Создай ровно один Inbox item без проекта, дат, приоритета, длительности или добавленного содержания. Даты и другие детали внутри исходного текста оставь текстом. Если создание требует дополнительных значений, не назначай их по догадке.
3. Сообщи, что запись сохранена во Inbox, и покажи её ID.

Не записывай обычный вопрос или справочный ответ без просьбы сохранить. Если текста нет, уточни, что записать. Явно выбранные несколько отдельных записей сохраняй без классификации как группу операций.

## Triage: один Inbox item за раз

1. Прочитай выбранный Inbox item и его ID; если их несколько, выбери с пользователем один. Прочтение ещё не означает завершённый Triage.
2. Определи тип: Задача, Проект, Идея, Справка или Встреча. Пока пользователь не разрешил неоднозначность, оставь запись во Inbox.
3. Для Задачи или Проекта уточни чистовую формулировку и доступность первого действия, затем выбери место по актуальному [дереву](tree.md). Одинаковые названия различай по пути и ID.
4. Покажи Preview: исходный ID, новая формулировка, место и выбранные дополнительные поля. После подтверждения измени исходную запись, сохранив ID; не создавай копию прежней формулировки.
5. Подтверди получившееся место и тот же ID. Не переходи автоматически к следующему Inbox item.

Отказ от формулировки оставляет запись без изменения. Отказ от самого действия или обязательства выполняй по [правилам состояния Задачи](projects.md).

## Сформулируй Задачу

Проверь конкретный глагол, объект и видимый признак готовности: «Отправить Анне смету; письмо со сметой отправлено». Признак готовности сохраняй в поддержанном тексте задачи. Не превращай неопределённое «заняться ремонтом» в список обещаний. Несколько самостоятельных действий для результата означают Проект.

Проверь, можно ли начать сейчас. Если задача зависла, спроси, что делает шаг неприятным или трудным, и предложи меньший шаг, уточнение недостающего ресурса или отказ от обязательства. Не ставь диагноз и не обещай выполнение после редактирования. По желанию пользователя предложи if–then: «если [наблюдаемая ситуация], то [доступное действие]», без обязательной даты.

## Преврати многошаговое дело в Проект

1. Уточни результат, место и следующий шаг по [правилам Проекта](projects.md). Если шаг неизвестен, согласуй конкретное действие по его определению.
2. Если подходящий проект уже есть, предложи поместить туда исходный Inbox item, без дубликата проекта.
3. Для нового проекта покажи одну группу операций: создать проект в выбранной области или папке, получить его ID, преобразовать исходный Inbox item в следующий шаг и поместить туда. В Preview укажи будущую привязку ID проекта и сохранение исходного ID задачи. Создание начинается только после подтверждения группы.
4. Дополнительный выбранный пользователем следующий шаг включи в ту же группу по правилам Проекта; если выбор сделан позже, обнови Preview до дополнительных записей.

При частичном результате может остаться проект без шага, а исходная запись — во Inbox; покажи фактическое положение каждого объекта. Для режима `когда-нибудь` применяй исключение из [правил дерева](tree.md); согласуй смысл и формулировку исходной записи в этом проекте.

## Идея, Справка или Встреча

1. Дай пользователю инструкцию переноса: Идею — туда, где решает, стоит ли действовать; Справку — туда, где найдёт информацию; Встречу — в свой календарь. Перенос выполняет пользователь.
2. До сообщения о завершённом переносе оставь исходный Inbox item без изменения. Намерение перенести не означает завершения.
3. После сообщения о завершении покажи Preview отмены с исходным ID и получи подтверждение. Выполни `task_cancel`; подтверждай отмену по возвращённому состоянию и описанной текущим инструментом семантике, без предположений о поле или enum задачи. Подтверждение переноса не заменяет подтверждение Preview отмены.

Не удаляй запись и не отмечай её выполненной. Если для Встречи ещё нужно уточнить время, место, участников или повестку, предложи тип Задача с действием уточнения; не создавай дополнительную задачу автоматически.

## Даты, приоритет и длительность

- Срок (`deadline`) — внешний жёсткий срок с последствиями пропуска. Плановая дата (`start`) — выбранный пользователем день начала. Не превращай прогноз в Срок и не переноси задачу молча.
- Даты, приоритет и длительность выбирает пользователь; существующие поля сохраняй, если их изменение не выбрано. Не обнуляй их ради чистовой формулировки.
- Срочность обсуждай через цену пропуска срока, а не только близость даты. Приоритет — выбор пользователя; его числовой контракт задан правилами записи.
- Оценка длительности — прогноз с неопределённостью, не обязательство. Сохраняй её по выбору пользователя в поддержанном поле; не назначай универсальную длительность или множитель.
