# Capture и Triage

Записи — по [правилам записи](write-policy.md).

## Возможности сценария

Для Capture нужны создание задачи во Inbox и чтение созданной записи. Для Triage — чтение Inbox, выбранной задачи и дерева, изменение текста и места задачи с сохранением ID. Для нового проекта дополнительно нужны создание проекта с назначением родителя и чтение результата; для отказа или перенесённых записей — `task_cancel` и чтение состояния задачи. Даты, приоритет, длительность и полезный текст изменяй только когда они выбраны для сценария.

## Capture: запиши сразу

1. На явную просьбу «запиши», «сохрани во Inbox» или равнозначную команду возьми текст как есть, без Triage и требования чистовой формулировки.
2. Создай ровно один Inbox item без проекта, дат, приоритета, длительности или добавленного содержания. Даты и другие детали внутри исходного текста оставь текстом. Если создание требует дополнительных значений, не назначай их по догадке.
3. Сообщи, что запись сохранена во Inbox, и покажи её ID.

Не записывай обычный вопрос или справочный ответ без просьбы сохранить. Если текста нет, уточни, что записать. Явно выбранные несколько отдельных записей сохраняй без классификации как группу операций.

## Triage: один Inbox item за раз

1. Прочитай выбранный Inbox item и его ID. Если записей несколько и выбор не задан, включи выбор в сообщение с блокирующими пробелами. Прочтение ещё не означает завершённый Triage.
2. Определи тип: Задача, Проект, Идея, Справка или Встреча. Используй уже заданный тип; при неоднозначности оставь запись во Inbox до ответа.
3. Для Задачи или Проекта используй заданные чистовую формулировку, первый доступный шаг и место по актуальному [дереву](tree.md). Собери только блокирующие пробелы одним сообщением. Одинаковые названия различай по пути и ID.
4. Полную явную команду выполни сразу, сохранив исходный ID; не создавай копию прежней формулировки. Для изменения, предложенного агентом, — одна строка и «да»; для набора, собранного агентом, — один Preview по правилам записи.
5. Через Read-back подтверди получившееся место и тот же ID. Следующую запись разбирай только если она входит в выбранный пользователем набор; обрабатывай его последовательно без отдельного вопроса о продолжении.

Отказ от формулировки оставляет запись без изменения. Отказ от самого действия или обязательства выполняй по [правилам состояния Задачи](projects.md).

## Сформулируй Задачу

Проверь конкретный глагол, объект и видимый признак готовности: «Отправить Анне смету; письмо со сметой отправлено». Признак готовности сохраняй в поддержанном тексте задачи. Не превращай неопределённое «заняться ремонтом» в список обещаний. Несколько самостоятельных действий для результата означают Проект.

Проверь, можно ли начать сейчас. Если задача зависла, используй известное препятствие и предложи меньший шаг, уточнение недостающего ресурса или отказ от обязательства. Спрашивай только то, без чего нельзя выбрать действие; объяснение трудного старта не обязательно. Глубокое уточнение намерения передавай `grill-me` средствами хоста; при его отсутствии рекомендуй установить, своё интервью не проводи. Не ставь диагноз и не обещай выполнение после редактирования. По желанию пользователя предложи if–then: «если [наблюдаемая ситуация], то [доступное действие]», без обязательной даты.

## Преврати многошаговое дело в Проект

1. Используй известные результат, место и следующий шаг по [правилам Проекта](projects.md); все блокирующие пробелы собери одним сообщением. Если шаг неизвестен, предложи конкретное действие по его определению.
2. Если подходящий проект уже есть, предложи поместить туда исходный Inbox item, без дубликата проекта.
3. Для нового проекта выполни группу: создать проект в выбранной области или папке, получить его ID, преобразовать исходный Inbox item в следующий шаг и поместить туда. Полную явную команду выполни без Preview; для набора, собранного агентом, покажи один Preview с будущей привязкой ID проекта и сохранением исходного ID задачи и получи одно подтверждение.
4. Дополнительный выбранный пользователем следующий шаг включи в ту же группу по правилам Проекта. Позднюю полную явную команду выполни сразу; новые предложения агента согласуй по правилам записи.

При частичном результате может остаться проект без шага, а исходная запись — во Inbox; покажи фактическое положение каждого объекта. Для режима `когда-нибудь` применяй исключение из [правил дерева](tree.md); используй заданные смысл и формулировку исходной записи, уточни только блокирующую неоднозначность.

## Идея или Справка

1. Дай пользователю инструкцию переноса: Идею — туда, где решает, стоит ли действовать; Справку — туда, где найдёт информацию. Перенос выполняет пользователь.
2. До сообщения о завершённом переносе оставь исходный Inbox item без изменения. Намерение перенести не означает завершения.
3. Для Идеи, Справки или уже вручную перенесённой Встречи «перенёс, отмени» при однозначном исходном ID — сразу `task_cancel` и Read-back. На одно «перенёс» ответь одной строкой: «Отменить Inbox item <ID>?»; выполни по «да». Не удаляй запись и не отмечай её выполненной. Отмену подтверждай чтением состояния по текущей семантике инструмента, без предположений о поле или enum задачи.

## Встреча из Inbox

1. Передай Встречу `jedikit-calendar` средствами хоста, с исходным ID и известными данными. До записи фактически загрузи его `SKILL.md` и правила записи; календарные операции выполняй по ним. Не объявляй передачу состоявшейся без загрузки скилла. Если скилл недоступен, назови ограничение и оставь Inbox item.
2. Недостающие обязательные поля События собирает `jedikit-calendar` одним сообщением; известное и необязательное не спрашивай. Если пользователь не знает дату или договорённости нет, предложи одной строкой сохранить это как Задачу с действием уточнения и выполни по «да».
3. Для явной полной команды переноса создание События и отмена Inbox item выполняются последовательно без Preview. Если набор собран агентом, включи обе операции в один общий Preview. После успешного создания и Read-back События выполни `task_cancel` исходного ID и Read-back состояния задачи. Если Событие не создалось или Read-back не подтвердил его, Inbox item оставь без изменения; при ошибке отмены сообщи, что Событие создано, а исходная запись не отменена либо её состояние неизвестно. Без автоматического повтора или отката.

Не удаляй Inbox item и не отмечай его выполненным. Сообщение пользователя не подтверждает успех незавершённой записи через `jedikit-calendar`; ручной перенос обрабатывай по правилу выше.

## Даты, приоритет и длительность

- Срок (`deadline`) — внешний жёсткий срок с последствиями пропуска. Плановая дата (`start`) — выбранный пользователем день начала. Не превращай прогноз в Срок и не переноси задачу молча.
- Даты, приоритет и длительность выбирает пользователь; существующие поля сохраняй, если их изменение не выбрано. Не обнуляй их ради чистовой формулировки.
- Срочность обсуждай через цену пропуска срока, а не только близость даты. Приоритет — выбор пользователя; его числовой контракт задан правилами записи.
- Оценка длительности — прогноз с неопределённостью, не обязательство. Сохраняй её по выбору пользователя в поддержанном поле; не назначай универсальную длительность или множитель.
