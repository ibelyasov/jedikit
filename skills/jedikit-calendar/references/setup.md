# Настройки календаря и status

Подключение Google Calendar, OAuth, scopes и установку инструментов выполняет владелец средствами хоста. Скилл использует существующее подключение `google_calendar`, не создаёт служебный календарь и не запрашивает секреты. Недостающие базовые имена назови по [tools.json](../tools.json); синтаксис — [calendar-tools.md](calendar-tools.md).

## Что хранить

Во встроенной памяти хоста храни только настройки:

| Настройка | Значение |
| --- | --- |
| Домашний часовой пояс | Один IANA timezone, например `Europe/Moscow`; используй известный пояс пользователя, не выводи его из языка |
| Календарь записи | Один выбранный календарь, по умолчанию `primary`; фактический ID и аккаунт нужны для однозначности |
| Календари чтения | Выбранные ID/аккаунты; по умолчанию все видимые, перечитываемые через `list-calendars`, а не однажды сохранённый снимок списка |
| Границы дня | Начало и конец для отображения окон, например 08:00–22:00; пример не является default или нормой |
| Зазор | Выбранная пользователем длительность между Бронью и Событием/Распорядком; без научного норматива |

Не сохраняй содержимое календаря, ID событий, состояние дня, историю сводок, Брони или Отметки. Источник состояния — провайдер. Зазор не создаёт буферных событий и не разрешает двигать Распорядок. Бронь — время под задачу со строкой `JediKit · Бронь · задача: <название задачи>`; задача не копируется в календарь, её состояние и выполнение остаются в SingularityApp.

## Setup и обычные фразы

1. Прочитай уже известные настройки. Через `list-calendars` узнай видимые календари, их ID, аккаунты и доступ записи из фактического ответа. Если право записи не видно, так и укажи; не проверяй его пробной записью. Чтение нескольких календарей не разрешает запись в них.
2. Используй defaults календарей без лишнего переспроса. При нескольких аккаунтах и неоднозначном `primary` уточни выбранный личный аккаунт. Домашний пояс, границы дня и зазор не выдумывай; незаданный зазор при расчёте считай нулевым и показывай это, не сохраняя как настройку. Для setup все отсутствующие нужные настройки спроси одним сообщением; для отдельного сценария — только блокирующие его поля. Просмотр записей возможен без границ дня, но окна без них не вычисляй. Не спрашивай зазор ради обычного События или вида.
3. Явные фразы вроде «мой день с 8 до 22», «живу по Москве», «читай эти календари, пиши в основной» распознавай как изменение настроек. Полную команду выполни сразу по [operation-policy.md](operation-policy.md); предложение значения агентом требует согласия по тем же правилам. Относительные даты не превращай в настройки.
4. Сохрани только выбранные настройки штатным механизмом памяти хоста и перечитай их. Покажи сохранённое и отсутствующее. Если памяти/Read-back нет, скажи об этом: названные значения можно использовать в текущем запросе, но не обещать сохранение.

Один домашний пояс применяй к «сегодня», диапазонам вида и отчётам. Пояс отдельного События, названный пользователем, не меняет домашний. Не принимай timezone календаря за домашний без данных пользователя. Для перехода полуночи используй следующую дату; если границы дня сами пересекают полночь, явно укажи это в показанном диапазоне.

## Status

Покажи настройки, недостающие значения и доступность нужных инструментов по списку хоста. При запросе о календарях выполни `list-calendars` и сообщи фактически прочитанный охват/ошибки. Не объявляй OAuth или возможность записи проверенными по одному наличию tool; если чтение успешно, назови только это чтение. Не создавай тестовых Событий и не меняй настройки в status.

`help` — краткая карта возможностей и примеры «покажи завтра», «запиши приём завтра в 15:00 на час», «добавь сон ежедневно с 23:00 до 07:00». Для help обращение к аккаунту не нужно. Утреннюю сводку запускает расписание владельца; setup скилла не настраивает cron, и фоновые запуски не сохраняют настройки.
