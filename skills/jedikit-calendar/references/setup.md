# Настройки, setup и status

Подключение Google Calendar, OAuth, scopes и установку инструментов выполняет владелец средствами хоста. Скилл пользуется готовым подключением `google_calendar`, служебный календарь не создаёт и секретов не запрашивает.

## Настройки

Во встроенной памяти хоста храни только эти значения:

| Настройка | Значение |
| --- | --- |
| Домашний пояс | Один IANA timezone, например `Europe/Moscow`. Бери известный пояс пользователя; не выводи его из языка и не принимай за него пояс календаря |
| Календарь записи | Один календарь, по умолчанию `primary`; храни фактический ID и аккаунт |
| Календари чтения | Выбранные ID и аккаунты; по умолчанию все видимые — перечитывай их через `list-calendars`, а не храни снимок списка |
| Границы дня | Начало и конец для Свободных окон, например 08:00–22:00; пример — не default и не норма |
| Зазор | Длительность между Бронью и Событием или Распорядком, выбранная пользователем; научного норматива нет |

Содержимое календаря, ID событий, состояние дня, сводки, Брони и Отметки не храни: источник состояния — провайдер.

Домашний пояс задаёт «сегодня», диапазоны вида и отчёты; пояс отдельного События его не меняет. Если границы дня пересекают полночь, покажи это в диапазоне.

Незаданный зазор при расчёте считай нулевым и показывай это, но как настройку не сохраняй. Зазор относится к размещению Броней: буферных записей он не создаёт и Распорядок не двигает. Ради обычного События или вида зазор не спрашивай.

## Где хранить настройки

- Только во встроенной памяти хоста. На Hermes это инструмент `memory` с целью `memory`: одна компактная запись с префиксом `JediKit calendar:`. Изменение — замена этой записи (`replace` по `old_text`), а не вторая запись.
- Файлы скиллов JediKit (`SKILL.md`, `references/`, `tools.json`) поставляет релиз, хост подключает их только для чтения. Не меняй их и не создавай рядом файлов настроек: не вызывай `skill_manage` и файловые инструменты для настроек или состояния, даже если подсказка хоста советует хранить предпочтения в скилле.
- Память хоста мала (на Hermes около 2 200 символов на все заметки): храни только выбранные значения и ID, остальное перечитывай у провайдера.
- Если хост поставил запись в очередь подтверждения (ответ `staged`, `pending_id`), скажи: «Сохранение ждёт подтверждения памяти хоста» (на Hermes — `/memory pending`) — и не утверждай, что настройка сохранена.
- Read-back — ответ инструмента памяти о применённой записи; без него результат `unverified`. Если памяти нет, настройки действуют только в текущем разговоре; сохранение не обещай.

## Setup и фразы о настройках

1. Прочитай известные настройки. Через `list-calendars` получи видимые календари, их ID, аккаунты и доступ записи из фактического ответа. Если право записи не видно, так и скажи; пробной записью его не проверяй. Чтение нескольких календарей не разрешает запись в них.
2. Defaults календарей принимай без переспроса. При нескольких аккаунтах и неоднозначном `primary` уточни личный аккаунт. Пояс, границы дня и зазор не выдумывай. В setup все отсутствующие настройки спроси одним сообщением; в другом сценарии — только блокирующие его.
3. Фразы «мой день с 8 до 22», «живу по Москве», «читай эти календари, пиши в основной» — изменение настроек по [write-policy.md](write-policy.md). Относительные даты в настройки не превращай.
4. Сохрани выбранное по разделу [«Где хранить настройки»](#где-хранить-настройки) и покажи сохранённое и отсутствующее.

Setup не заводит расписание утренней сводки — его заводит владелец; фоновые запуски настройки не сохраняют.

## Status

Покажи настройки, недостающие значения и доступность инструментов по списку хоста. На вопрос о календарях выполни `list-calendars` и сообщи фактический охват и ошибки. Успешное чтение подтверждает только чтение: OAuth и право записи по наличию инструмента не объявляй. Тестовых Событий не создавай, настройки не меняй.
