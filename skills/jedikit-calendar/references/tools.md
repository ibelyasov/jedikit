# Инструменты Google Calendar

Инструменты даёт MCP-сервер `google_calendar` в Hermes; разрешённый набор — [tools.json](../tools.json) (загрузка — `skill_view(name="<имя этого скилла>", file_path="tools.json")`). Схемы взяты из [`nspady/google-calendar-mcp` v2.7.0](https://github.com/nspady/google-calendar-mcp/tree/3c3c36e129e2ff9fcd395a42578b057e6d85f721) (npm `@cocal/google-calendar-mcp` 2.7.0) — стороннего MCP, а не сервера Google. Чтение нескольких календарей, вхождения серии с их ID, три режима серии, удаление, ответы о дублях и конфликтах подтверждены живыми вызовами сервера; работа через модель, срок жизни авторизации и пагинация реализации не проверены.

## Подключение

Callable name — `mcp__google_calendar__<name>`, любой символ вне `[A-Za-z0-9_]` заменяется на `_`: `get-event` — `mcp__google_calendar__get_event`, `get-current-time` — `mcp__google_calendar__get_current_time`. Вызывай только имя, у которого часть после префикса совпадает с базовым `name`.

Если нужный MCP-инструмент виден напрямую, вызывай его по callable name. Иначе schemas отложены Tool Search, и отсутствие инструмента в видимом списке не значит, что его нет: найди нужные `tool_search(queries=[…])`, получи schemas группой `tool_describe(names=[…])`, вызывай `tool_call(calls=[{name, arguments}])` — один MCP-вызов в `calls` за раз. Если точное имя известно, начни с `tool_describe`.

Если нужных инструментов нет, назови их базовые имена и порекомендуй подключить их в Hermes. OAuth, scopes и конфигурацию не меняй; инструменты не обходи через REST, terminal или собственный код. Проверяй только инструменты, нужные сценарию: весь каталог ради одного чтения не требуй. Наличие инструмента не доказывает авторизацию.

## Чтение

| Инструмент | Аргументы |
| --- | --- |
| `get-current-time` | `timeZone` — домашний пояс IANA. Вызывай перед любым «сегодня», относительной датой, поиском, созданием или изменением |
| `list-calendars` | Обязательных нет. `account` — nickname или массив 1–10; без него читаются все подключённые аккаунты. В ответе у каждого календаря `defaultReminders` (`method`, `minutes`) |
| `list-events` | `calendarId` — ID или массив 1–50 ID без повторов; бери ID из `list-calendars`, а не неоднозначное имя. `timeMin`, `timeMax` — ISO 8601 без смещения; `timeZone` — IANA; `fields`; `account` — строка или массив |
| `get-event` | `calendarId`, `eventId` — строки; `fields`; `account` — строка |

Nickname соответствует `^[a-z0-9_-]{1,64}$`. При нескольких аккаунтах передавай nickname аккаунта календаря: `primary` без него неоднозначен.

Без `fields` сервер не ставит маску и возвращает событие целиком. С `fields` он добавляет к названным полям default-набор: `id`, `summary`, `start`, `end`, `status`, `htmlLink`, `location`, `attendees`, `reminders`, `recurrence`. Метки роли и остальных признаков серии в нём нет, поэтому всегда запрашивай `fields: ["description", "recurringEventId", "originalStartTime", "recurrence", "transparency"]`; перед update/delete добавь `organizer`, при необходимости `updated`, `locked`. Для [напоминаний](#напоминания) явно называй `reminders` в `fields`: повтор поля безвреден. Для [цвета](#цвета), в том числе Read-back и перекраски, называй `colorId` явно: в default-набор он не входит.

Пагинации нет: `pageToken`, `maxResults`, `singleEvents`, `orderBy` и текстового поиска в схеме нет, не передавай их. Кандидатов отбирай из ответа за диапазон `timeMin`/`timeMax`. Больше 50 календарей читай несколькими запросами. Проверяй ошибки отдельных календарей и признаки усечения: при усечении сужай диапазон, а если это невозможно, честно ограничь охват. Отсутствие объекта в неполной выборке ничего не доказывает; схема входа не гарантирует структуру ответа.

## Запись

| Инструмент | Поля |
| --- | --- |
| `create-event` | `calendarId`, `summary`, `start`, `end`; по сценарию `timeZone`, `description`, `location`, `recurrence`, `reminders`, `colorId`, `calendarsToCheck`, `allowDuplicates`; `sendUpdates` |
| `update-event` | `calendarId`, `eventId`; только изменяемые `summary`, `description`, `location`, `start`, `end`, `timeZone`, `recurrence`, `reminders`, `colorId`; для серии `modificationScope`, `originalStartTime`, `futureStartDate`; при смене времени `checkConflicts`, `calendarsToCheck`; `sendUpdates` |
| `delete-event` | `calendarId`, `eventId`, `sendUpdates`. Полей режима серии нет |

`account` у записей — строка. `sendUpdates: "none"` передавай явно во всех трёх: у update/delete default — `all`. Участники, конференции, вложения, управление гостями и `extendedProperties` вне скилла.

### Даты

- Событие со временем: `YYYY-MM-DDTHH:MM:SS` без смещения плюс `timeZone` IANA. Смещение в строке перекрывает `timeZone`, поэтому не смешивай их. JSON-строка с `dateTime`/`timeZone`, которую допускает схема, в сценариях скилла не нужна.
- Весь день: `YYYY-MM-DD`, `end` эксклюзивный — однодневное Событие заканчивается следующей датой.
- Конец позже начала; переход через полночь — следующей датой. Возвращённые даты читай по фактическому формату, не отбрасывая пояс.

### Повтор и режимы серии

`recurrence` — массив строк RFC 5545, например `["RRULE:FREQ=WEEKLY;BYDAY=TU"]`. Передавай только правило с понятной семантикой; окончание серии не выдумывай.

| `modificationScope` | Что нужно |
| --- | --- |
| `thisEventOnly` | ID серии и `originalStartTime` выбранного вхождения |
| `thisAndFollowing` | ID серии и `futureStartDate` первого изменяемого вхождения |
| `all` | ID серии |

`list-events` возвращает вхождения серии отдельными записями: собственный `id` экземпляра, `recurringEventId` (ID серии) и `originalStartTime`. ID экземпляра и серии бери из ответа, не конструируй из даты.

`originalStartTime` и `futureStartDate` — исходное время вхождения по правилу серии, а не время после переноса ([Google](https://developers.google.com/workspace/calendar/api/guides/recurringevents)). Передавай их **со смещением** (`+03:00` или `Z`): бери `originalStartTime.dateTime` вхождения из ответа как есть. Без смещения сервер ищет экземпляр по времени UTC и возвращает `Not Found`. У серии на весь день `originalStartTime.date` передавай как есть, время не дописывай; при `Not Found` назови ограничение. Это исключение из правила «время без смещения плюс `timeZone`» для `start`/`end`.

`thisAndFollowing` делит серию: старая часть получает `UNTIL`, новая — новый ID и копию исходного `recurrence`. Если правило ограничено `COUNT`, сервер его не пересчитывает и серия удлиняется: в том же вызове передай `recurrence` новой части с `UNTIL` прежнего последнего вхождения (пересчёт `COUNT` ненадёжен при исключениях). После вызова перечитай обе части; если правило новой части не совпало с ожидаемым, результат `unverified` — остановись и не повторяй запись. После разделения части — независимые События: удаление или `all` по одному ID затрагивает только его часть. `all` по ID старой части меняет только её, включая ранее изменённые вхождения.

## Конфликты и дубли

`calendarsToCheck` — массив ID календарей; при создании и смене времени передавай календари чтения, иначе проверка ограничится календарём записи. У update при смене времени передавай `checkConflicts: true`. Для собственного показа пересечений читай затронутый диапазон; это не защищает от гонок. Конфликт запись не блокирует: create/update выполняются, а рядом с `event` в ответе приходят `conflicts` (событие, календарь, пересечение) и `warnings` при `isError: false`. Поэтому пересечения считай сам по прочитанному диапазону до записи: набор, собранный агентом, показывает их в Preview; полная явная команда выполняется, а конфликты из ответа попадают в отчёт. Другие записи не двигай, проверку ради успеха не отключай.

`create-event` с `allowDuplicates: false` (default) блокирует почти точный дубль с similarity ≥ 0.95: `isError: true` и текст `Duplicate event detected (…% similar). Event "…" already exists…`. Похожее событие с similarity от `duplicateSimilarityThreshold` (default 0.7) создаётся, а в ответе приходят `duplicates` и `warnings` — покажи их в отчёте; порог не ослабляй. При отказе покажи найденное Событие одной строкой; ID дубля, если его нет в ответе, не придумывай. `allowDuplicates: true` передавай только после «создай всё равно» и после того, как результат предыдущего вызова установлен.

## Напоминания

`reminders` — объект `{useDefault, overrides}`. Элемент `overrides` — `{method, minutes}`: `method` — `popup` (default) или `email`, `minutes` — 0–40320 минут до начала; не больше 5 элементов. Набор вне этих пределов не передавай: назови ограничение и уточни набор вместе с прочими блокирующими пробелами. Напоминания приватны: срабатывают только у владельца календаря и гостям не отправляются; отдельного подтверждения сверх [правил записи](write-policy.md) не нужно.

| Значение | `reminders` |
| --- | --- |
| Как в календаре | При создании не передавай — действуют умолчания календаря; при изменении — `{"useDefault": true, "overrides": []}` |
| Свой набор | `{"useDefault": false, "overrides": [{"method": "popup", "minutes": 60}, {"method": "popup", "minutes": 1440}]}` |
| Без напоминаний | `{"useDefault": false, "overrides": []}` |

**Создание.** Значение берётся из настройки типа записи в записи памяти `JediKit calendar:`: «Напоминания Событий», «Напоминания Броней» или «Напоминания Распорядка»; незаданная — «как в календаре». Явное указание в запросе («напомни за 15 минут») сильнее настройки и задаёт набор этой записи; способ не назван — `popup`.

**Событие на весь день.** `defaultReminders` из `list-calendars` относятся к записям со временем; умолчания all-day задаются в интерфейсе Google и через сервер не видны, а `minutes` у all-day отсчитываются от 00:00 дня. Поэтому настройка «Напоминания Событий» к all-day не применяется: при создании `reminders` не передавай, кроме явной просьбы.

**Изменение** существующей записи — только по явной просьбе: заменить набор, убрать напоминания, «как обычно» (`{"useDefault": true, "overrides": []}`: пустой массив заменяет прежние `overrides`, иначе patch может быть отклонён или сохранить прежние `overrides`) или добавить и убрать отдельные напоминания. При переносе и других изменениях `reminders` не передавай. `update-event` патчит событие, но массив `overrides` заменяется целиком. Поэтому для «добавь ещё за сутки» или «убери то, что за час» сначала прочитай текущие `reminders` через `get-event`; если там `useDefault: true`, действующий набор — `defaultReminders` календаря из `list-calendars`, а у all-day он неизвестен: отдельное напоминание не добавляй и не убирай, назови ограничение и предложи задать полный набор. Передай полный новый набор. У серии режим и его поля — как при других изменениях серии ([«Повтор и режимы серии»](#повтор-и-режимы-серии)).

**Read-back** — `get-event` с `reminders` в `fields`: сверь `useDefault` и набор `overrides` без учёта порядка. Read-back подтверждает конфигурацию, а не доставку уведомления.

Смена настройки уже созданные записи не меняет. `defaultReminders` самого календаря скилл изменить не может: в сервере нет инструмента для настроек календаря. На такую просьбу так и скажи: они меняются в настройках Google Calendar — настройки календаря → «Уведомления о мероприятиях». Изменения не обещай.

## Цвета

Каждая создаваемая запись — Событие, Бронь, Распорядок — получает `colorId` по одной оси: смыслу занятия. Схема фиксирована в скилле и не хранится в настройках. Цвет не спрашивай и не считай блокирующим пробелом: категорию выбери сам по порядку вопросов; исключение — неоднозначный цвет словами. Цвет — личное оформление: гости его не видят, видят те, кто может изменять календарь ([справка Google](https://support.google.com/calendar/answer/72143?hl=en)); отдельного подтверждения сверх [правил записи](write-policy.md) не нужно. `colorId` (строка) в `create-event` и `update-event` и в `fields` list/get подтверждён чтением source v2.7.0, живыми вызовами не проверялся.

| Категория | Что входит | `colorId` |
| --- | --- | --- |
| Встречи | Договорённости с людьми по делу, в том числе рабочие созвоны | `9` Blueberry |
| Общение | Друзья, близкие, свидания, семья | `1` Lavender |
| Работа и фокус | Работа, свои проекты, планирование, рефлексия | `5` Banana |
| Обучение | Любое обучение, в том числе по работе | `6` Tangerine |
| Заряд | Спорт, хобби — активное и наполняющее | `10` Basil |
| Досуг | Сериал, игры, кино — развлечение без усилия | `7` Peacock |
| Покой | Сон, отдых, духовная практика | `2` Sage |
| База | Врач, анализы, финансы, налоги, документы, госуслуги | `3` Grape |
| Рутина | Дорога, еда, быт, покупки — всё остальное | `8` Graphite |

`11` Tomato и `4` Flamingo схема не использует. Цвета называй категорией, номером и английским именем; русские названия цветов Google не выдумывай. Именованных labels Google (`eventLabelId`) у сервера нет: легенда — эта таблица.

**Имена категорий в Google.** Если пользователь хочет видеть категории в интерфейсе, подскажи: один раз вручную назвать в Google Calendar ярлык каждого цвета схемы именем его категории по таблице. Записи и их `colorId` от этого не меняются. Оттенок встроенного цвета менять не советуй: по наблюдению сообщества у записей с пользовательским цветом может не быть `colorId`, и скилл не сможет такой цвет поставить; для перекраски встроенного цвета это не проверено. Сам скилл ярлыки не создаёт и не переименовывает: сервер этого не умеет.

**Категория.** Иди по порядку, срабатывает первая подходящая: 1 Покой → 2 Обучение → 3 База → 4 Встречи → 5 Общение → 6 Работа и фокус → 7 Заряд → 8 Досуг → 9 Рутина. Например, созвон с ментором по курсу — Обучение, приём у врача — База, тренировка с другом — Общение. Названная пользователем категория или цвет сильнее порядка. Бронь красится по содержанию Задачи, а не по роли: Бронь «подать декларацию» — База. Распорядок — по тому, что даёт действие или ритуал: сон — Покой, тренировка — Заряд. Своего цвета у роли нет.

**Цвет словами.** Названные категорию, ID или английское имя (`Basil`, «colorId 10») используй как есть. Цвет словами, однозначно соответствующий одному ID схемы, бери как этот ID: «серым» — `8`, «жёлтым» — `5`, «оранжевым» — `6`. Если цвет словами подходит нескольким ID и категория по порядку вопросов входит в их число, бери её без вопроса: тренировка «зелёным» — Заряд `10`. Явно названный цвет вне схемы (`11` Tomato, `4` Flamingo) используй как назван. Иначе, например созвон по делу «зелёным» — Basil или Sage, включи выбор в общий `clarify` запроса.

**Создание.** Передай `colorId` категории в `create-event`; у серии он действует на все вхождения.

**Изменение** цвета существующей записи — только по явной просьбе. Одиночная явная команда («покрась тренировку в Заряд») выполняется сразу. «Перекрась календарь по схеме» — набор агента: диапазон должен быть назван, иначе это блокирующий пробел. Прочитай диапазон календаря записи с `colorId` в `fields`, вхождения одной серии объедини по `recurringEventId` и покажи один Preview: запись, категорию, старый → новый `colorId`, режим серии ([«Повтор и режимы серии»](#повтор-и-режимы-серии)). Серию предлагай перекрасить в режиме `all` и в Preview прямо скажи, что меняются все её вхождения, в том числе вне названного диапазона. Сервер не читает `eventLabelId`, поэтому отсутствие `colorId` не доказывает, что запись не окрашена вручную label Google, а взаимодействие `colorId` с назначенной label не проверено: в Preview прямо скажи об этом. Записи, у которых в ответе уже есть `colorId`, в такой набор не включай, если пользователь явно не попросил перекрасить и их. Права, приглашения с другим организатором и записи вне календаря записи — по [остановкам](write-policy.md#остановки), как у других update. При переносе, переименовании и других изменениях `colorId` не передавай. Возврат к цвету календаря через сервер не проверен — не обещай его.

**Read-back** — `get-event` с `colorId` в `fields`: сверь значение. Read-back подтверждает конфигурацию, а не вид в интерфейсе.

Цвет не доказывает ни роль, ни категорию существующей записи: из цвета их не выводи.

## Метки ролей

Роль записи — одна видимая строка в `description`; других меток JediKit нет.

| Роль | Строка в описании |
| --- | --- |
| Бронь | `JediKit · Бронь · задача: <название задачи>`; ссылка или ID задачи, если есть, — указатель на задачу |
| Распорядок | `JediKit · Распорядок` — одиночное действие; `JediKit · Распорядок · ритуал: <название области Habitify>` — ритуал, название области — указатель для сдвига ритуала от `jedikit-habits` |
| Событие | Без метки |

Роль — по строке описания, начинающейся с `JediKit · Бронь` или `JediKit · Распорядок`; из названия, цвета или календаря её не выводи.
