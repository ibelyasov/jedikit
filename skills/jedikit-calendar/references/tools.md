# Инструменты Google Calendar

Инструменты даёт MCP-сервер `google_calendar` в Hermes; разрешённый набор — [tools.json](../tools.json) (загрузка — `skill_view(name="<имя этого скилла>", file_path="tools.json")`). Схемы взяты из [`nspady/google-calendar-mcp` v2.7.0](https://github.com/nspady/google-calendar-mcp/tree/3c3c36e129e2ff9fcd395a42578b057e6d85f721) (npm `@cocal/google-calendar-mcp` 2.7.0) — стороннего MCP, а не сервера Google. Чтение нескольких календарей, вхождения серии с их ID, три режима серии, удаление, ответы о дублях и конфликтах подтверждены живыми вызовами сервера; работа через модель, срок жизни авторизации и пагинация реализации не проверены.

## Подключение

Callable name — `mcp__google_calendar__<name>`, любой символ вне `[A-Za-z0-9_]` заменяется на `_`: `get-event` — `mcp__google_calendar__get_event`, `get-current-time` — `mcp__google_calendar__get_current_time`. Вызывай только имя, у которого часть после префикса совпадает с базовым `name`.

Если нужный MCP-инструмент виден напрямую, вызывай его по callable name. Иначе schemas отложены Tool Search, и отсутствие инструмента в видимом списке не значит, что его нет: найди нужные `tool_search(queries=[…])`, получи schemas группой `tool_describe(names=[…])`, вызывай `tool_call(calls=[{name, arguments}])` — один MCP-вызов в `calls` за раз. Если точное имя известно, начни с `tool_describe`.

Если нужных инструментов нет, назови их базовые имена и порекомендуй подключить их в Hermes. OAuth, scopes и конфигурацию не меняй; инструменты не обходи через REST, terminal или собственный код. Проверяй только инструменты, нужные сценарию: весь каталог ради одного чтения не требуй. Наличие инструмента не доказывает авторизацию.

## Чтение

| Инструмент | Аргументы |
| --- | --- |
| `get-current-time` | `timeZone` — домашний пояс IANA. Вызывай перед любым «сегодня», относительной датой, поиском, созданием или изменением |
| `list-calendars` | Обязательных нет. `account` — nickname или массив 1–10; без него читаются все подключённые аккаунты |
| `list-events` | `calendarId` — ID или массив 1–50 ID без повторов; бери ID из `list-calendars`, а не неоднозначное имя. `timeMin`, `timeMax` — ISO 8601 без смещения; `timeZone` — IANA; `fields`; `account` — строка или массив |
| `get-event` | `calendarId`, `eventId` — строки; `fields`; `account` — строка |

Nickname соответствует `^[a-z0-9_-]{1,64}$`. При нескольких аккаунтах передавай nickname аккаунта календаря: `primary` без него неоднозначен.

По умолчанию list/get возвращают `id`, `summary`, `start`, `end`, `status`, `htmlLink`, `location`, `attendees`. Метка роли и признаки серии в них не входят, поэтому всегда запрашивай `fields: ["description", "recurringEventId", "originalStartTime", "recurrence", "transparency"]`; перед update/delete добавь `organizer`, при необходимости `updated`, `locked`.

Пагинации нет: `pageToken`, `maxResults`, `singleEvents`, `orderBy` и текстового поиска в схеме нет, не передавай их. Кандидатов отбирай из ответа за диапазон `timeMin`/`timeMax`. Больше 50 календарей читай несколькими запросами. Проверяй ошибки отдельных календарей и признаки усечения: при усечении сужай диапазон, а если это невозможно, честно ограничь охват. Отсутствие объекта в неполной выборке ничего не доказывает; схема входа не гарантирует структуру ответа.

## Запись

| Инструмент | Поля |
| --- | --- |
| `create-event` | `calendarId`, `summary`, `start`, `end`; по сценарию `timeZone`, `description`, `location`, `recurrence`, `calendarsToCheck`, `allowDuplicates`; `sendUpdates` |
| `update-event` | `calendarId`, `eventId`; только изменяемые `summary`, `description`, `location`, `start`, `end`, `timeZone`, `recurrence`; для серии `modificationScope`, `originalStartTime`, `futureStartDate`; при смене времени `checkConflicts`, `calendarsToCheck`; `sendUpdates` |
| `delete-event` | `calendarId`, `eventId`, `sendUpdates`. Полей режима серии нет |

`account` у записей — строка. `sendUpdates: "none"` передавай явно во всех трёх: у update/delete default — `all`. Участники, напоминания, конференции, вложения, управление гостями и `extendedProperties` вне скилла.

### Даты

- Событие со временем: `YYYY-MM-DDTHH:MM:SS` без смещения плюс `timeZone` IANA. Смещение в строке перекрывает `timeZone`, поэтому не смешивай их. JSON-строка с `dateTime`/`timeZone`, которую допускает схема, в сценариях скилла не нужна.
- Весь день: `YYYY-MM-DD`, `end` эксклюзивный — однодневное Событие заканчивается следующей датой.
- Конец позже начала; переход через полночь — следующей датой. Возвращённые даты читай по фактическому формату, не отбрасывая пояс.

### Повтор и режимы серии

`recurrence` — массив строк RFC 5545, например `["RRULE:FREQ=WEEKLY;BYDAY=TU"]`. Передавай только правило с понятной семантикой; окончание серии не выдумывай.

| `modificationScope` | Что нужно |
| --- | --- |
| `thisEventOnly` | ID серии и `originalStartTime` выбранного вхождения |
| `thisAndFollowing` | ID серии и `futureStartDate` первого изменяемого вхождения |
| `all` | ID серии |

`list-events` возвращает вхождения серии отдельными записями: собственный `id` экземпляра, `recurringEventId` (ID серии) и `originalStartTime`. ID экземпляра и серии бери из ответа, не конструируй из даты.

`originalStartTime` и `futureStartDate` — исходное время вхождения по правилу серии, а не время после переноса ([Google](https://developers.google.com/workspace/calendar/api/guides/recurringevents)). Передавай их **со смещением** (`+03:00` или `Z`): бери `originalStartTime.dateTime` вхождения из ответа как есть. Без смещения сервер ищет экземпляр по времени UTC и возвращает `Not Found`. У серии на весь день `originalStartTime.date` передавай как есть, время не дописывай; при `Not Found` назови ограничение. Это исключение из правила «время без смещения плюс `timeZone`» для `start`/`end`.

`thisAndFollowing` делит серию: старая часть получает `UNTIL`, новая — новый ID и копию исходного `recurrence`. Если правило ограничено `COUNT`, сервер его не пересчитывает и серия удлиняется: в том же вызове передай `recurrence` новой части с `UNTIL` прежнего последнего вхождения (пересчёт `COUNT` ненадёжен при исключениях). После вызова перечитай обе части; если правило новой части не совпало с ожидаемым, результат `unverified` — остановись и не повторяй запись. После разделения части — независимые События: удаление или `all` по одному ID затрагивает только его часть. `all` по ID старой части меняет только её, включая ранее изменённые вхождения.

## Конфликты и дубли

`calendarsToCheck` — массив ID календарей; при создании и смене времени передавай календари чтения, иначе проверка ограничится календарём записи. У update при смене времени передавай `checkConflicts: true`. Для собственного показа пересечений читай затронутый диапазон; это не защищает от гонок. Конфликт запись не блокирует: create/update выполняются, а рядом с `event` в ответе приходят `conflicts` (событие, календарь, пересечение) и `warnings` при `isError: false`. Поэтому пересечения считай сам по прочитанному диапазону до записи: набор, собранный агентом, показывает их в Preview; полная явная команда выполняется, а конфликты из ответа попадают в отчёт. Другие записи не двигай, проверку ради успеха не отключай.

`create-event` с `allowDuplicates: false` (default) блокирует почти точный дубль с similarity ≥ 0.95: `isError: true` и текст `Duplicate event detected (…% similar). Event "…" already exists…`. Похожее событие с similarity от `duplicateSimilarityThreshold` (default 0.7) создаётся, а в ответе приходят `duplicates` и `warnings` — покажи их в отчёте; порог не ослабляй. При отказе покажи найденное Событие одной строкой; ID дубля, если его нет в ответе, не придумывай. `allowDuplicates: true` передавай только после «создай всё равно» и после того, как результат предыдущего вызова установлен.

## Метки ролей

Роль записи — одна видимая строка в `description`; других меток JediKit нет.

| Роль | Строка в описании |
| --- | --- |
| Бронь | `JediKit · Бронь · задача: <название задачи>`; ссылка или ID задачи, если есть, — указатель на задачу |
| Распорядок | `JediKit · Распорядок · ритуал: <название области Habitify>` или `JediKit · Распорядок · <действие>` |
| Событие | Без метки |

Роль не выводи из названия, цвета или календаря.
