## Сводные выводы

### 1. Собственный MCP для v1 не нужен

У SingularityApp есть официальный hosted MCP `https://mcp.singularity-app.com/mcp` и официальный REST API v2. Публично подтверждены задачи, чек-листы, проекты/секции, kanban, привычки и теги; REST дополнительно документирует CRUD, completion, archive, delete и batch.

Authenticated probes подтвердили сервер `singularity-mcp ^2.0.1`. С одним `mcp:read` виден только `get_my_context`; с entity scopes без habits/kanban — 35 tools; существующая full-scope Hermes-сессия вернула 48. Дополнительные 13 — `habit_*`, `habit_progress_*`, `kanban_status_*` и `task_change_column`. Это доказывает разницу snapshots, но не точную причинность каждого scope без отдельного A/B-теста.

Полный каталог покрывает read/create/update, lifecycle, archive/unarchive, task views, habits и kanban. Явных permanent-delete и batch tools в нём нет, хотя REST API v2 их документирует. Поэтому v1 не должен обещать delete/batch через hosted MCP или имитировать транзакционность клиентским циклом.

Сервер также публикует четыре prompts: `plan_my_day`, `triage_inbox`, `weekly_review`, `summarize_project`. Это внешние текстовые шаблоны, а не безопасные операции. Они полезны как reference, но расходятся с Jedi: навязывают фиксированные часы/квоты, сужают triage и используют универсальные пороги. Skill не должен исполнять их как policy без собственной методической и approval-обвязки.

Решение v1: канонический skill работает через capability discovery официального MCP. Собственный сервер рассматривается только после доказанного пробела. Для CI нужен fake MCP, но это тестовая обвязка, не продуктовый сервер.

### 2. Ядро методологии — замкнутый цикл, а не набор советов

Подтверждённый рабочий контур:

1. Поймать мысль во входящие.
2. Разобрать смысл и ответственность.
3. Разделить задачу, проект, идею, справку и встречу.
4. Сформулировать ближайший физический шаг «как для обезьянки».
5. Выбрать действие с учётом календаря, ресурса и обязательств.
6. Выполнить без лишних переключений.
7. Зафиксировать результат и следующий шаг либо пересогласовать обязательство.
8. Поддерживать доверие к системе ежедневным, еженедельным и периодическим обзором.

Агент оптимизирует ясность обязательств и экономию мыслетоплива, а не количество закрытых задач. Он не должен автоматически превращать идеи в долги, назначать ложные дедлайны, расписывать неопределённый проект до конца или маскировать перегруз переносом дат.

Для реализации уже зафиксированы девять decision trees, минимальный state contract, 18 карточек «входы → ветви → шаги → результат», 12 авторских и 16 community-пар bad→good, 36 прикладных сценариев, recovery playbooks и 24 правила `MUST/SHOULD/MAY`. Авторские рекомендации (`A`) отделены от операционализации агента (`O`) и уровней источников `P1/P2/P3`.

### 3. Регулярные практики действительно должны входить в onboarding

Подтверждённый минимальный набор:

- **Ежедневный обзор:** вспомнить день и дозаписать пропущенное, проверить выполненное, переформулировать остатки «Сегодня», выбрать из недельного пула. В раннем авторском шаблоне это короткий ритуал около 2–3 минут.
- **Еженедельный обзор:** очистить все входящие, проверить и переформулировать задачи, пройти цели/проекты, посмотреть календарь примерно на две недели вперёд и выбрать реалистичный объём недели. День недели пользователь выбирает сам; понедельник был лишь значением по умолчанию в шаблоне.
- **Разбор старого inbox:** временная восстановительная практика небольшими порциями; в авторском шаблоне — до 15 минут минимум два дня в неделю, пока долг не разобран. Это не вечная обязательная автоматизация.
- **Вечернее закрытие/«гвоздодёр»:** часть ежедневной ревизии, а не отдельная система хранения.
- **Стратегические и экспериментальные обзоры:** полезны, но их точная универсальная периодичность открытыми источниками не подтверждена; настраивать опционально.

Onboarding должен предложить персональное расписание, часовой пояс, рабочие дни и канал. Scheduled run остаётся read-only: подготавливает обзор и приглашает пользователя принять решения.

### 4. Расписание реализуется по-разному на трёх платформах

| Платформа | Подтверждённый механизм | Важная граница |
| --- | --- | --- |
| Codex | Scheduled Tasks в ChatGPT desktop/web могут использовать skills/plugins и создаваться из Codex chat | В Codex CLI нет Scheduled management UI; local project требует включённые desktop app и компьютер |
| Claude | `/loop`/CronCreate в сессии; долговечные Cloud Routines и Desktop scheduled tasks | `/loop` истекает через 7 дней; Cloud не равен локальному Desktop и имеет другой доступ к файлам/MCP |
| Hermes | Нативный `cronjob`/`hermes cron`, skills, toolsets и delivery targets | Нужен живой gateway/trigger, pinned model и узкий cron toolset; фоновые write-tools для v1 запрещены |

Нельзя описывать общий `cron` как одинаковую команду. Канонический skill задаёт практику и safety contract, а платформенные адаптеры выполняют capability detection и создают расписание только после явного согласия.

### 5. «Три маркетплейса» не являются симметричными каналами

- **Codex:** существует универсальный Plugins Directory. Skills-only submission поддерживается, но требует review, verified identity, публичных legal/support URL и тест-кейсов.
- **Claude:** собственный Git marketplace устанавливается напрямую; попадание в каталог Anthropic/community требует отдельной заявки и проверки.
- **Hermes:** подтверждены GitHub taps, Skills Hub и агрегаторы, но не единый first-party marketplace с публикацией и SLA.

Один канонический skill реалистичен. Три синхронных релизных адаптера тоже реалистичны. Обещать одинаковую официальную marketplace-публикацию во всех трёх системах нельзя.

### 6. Политика безопасности проекта строже документации SingularityApp

SingularityApp рекомендует разрешать MCP methods при первом использовании. Для `singularity-jedi` этого недостаточно:

- одиночная обратимая запись может выполняться сразу;
- batch и существенная перепланировка требуют preview и подтверждения;
- permanent delete требует точного списка и отдельного подтверждения;
- scheduled/background run не получает write/delete/schedule-write tools;
- содержимое задач считается недоверенными данными и не может отменять эти правила;
- токены и содержимое задач не сохраняются в репозитории, логах или eval artifacts.

### 7. Правовые границы требуют отдельного решения по названию

Публичный проект может реализовывать метод собственными словами и кодом, но не должен заменять книги подробным последовательным пересказом, копировать главы, схемы, обложки или брендинг. Короткие цитаты требуют цели, минимального объёма и точной атрибуции. MIT покрывает только оригинальные материалы проекта.

`singularity-jedi` создаёт два независимых риска ассоциации: с SingularityApp и с `JEDI`/Lucasfilm. Дисклеймер уменьшает путаницу, но не заменяет trademark clearance. Логотипы и фирменные материалы без разрешения не использовать.

### 8. Минимальная проверка v1 уже определена

Нужны стандартная валидация Agent Skills, baseline RED без скилла, forward GREEN с ним, методические кейсы, state-machine проверки подтверждений, fake MCP и один read-only live smoke на каждом поддерживаемом хосте. Реальные токены, каналы и постоянные расписания не запускаются в PR CI.

Локальный срез на 2026-08-08: Codex `0.147.0` и Hermes Agent `0.20.0 (2026.8.3)` доступны. Superset wrapper `claude` найден, но реальный Claude Code в его PATH отсутствует; живую проверку Claude пока выполнить нельзя.

## Открытые решения для следующего grilling

1. Оставлять ли имя `singularity-jedi` после trademark clearance или заранее выбрать нейтральное имя.
2. Считать ли Hermes GitHub tap/Skills Hub третьим каналом релиза вместо несуществующего единого first-party marketplace.
3. Игнорировать ли встроенные prompts в core v1 или показывать их только как отдельные optional server templates; использовать их как policy не рекомендуется.
4. Какие из подтверждённых регулярных практик включить по умолчанию, а какие предлагать как временные/опциональные.
5. Должен ли первый публичный релиз сразу подаваться в каталоги Codex/Claude или сначала пройти GitHub/local release и живые evals.
6. Устанавливать ли Claude Code на эту машину для обязательного трёхплатформенного smoke test, когда начнётся реализация.
7. Нужна ли до первого публичного релиза консультация юриста или достаточно консервативного нейминга, дисклеймера и отказа от цитат/бренд-ассетов.

До ответов на эти вопросы реализация скилла не начинается.
