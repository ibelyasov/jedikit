# Product decisions: JediKit Tasks for SingularityApp

**Актуально на:** 2026-08-09 (Europe/Moscow)

**Статус:** grilling завершён и подтверждён пользователем; `v0.1.0-alpha.1` реализован локально и проходит prerelease-проверки, публикация не выполнялась.

**Финальный бренд:** `JediKit`; package/repo slug `jedikit`; первый skill `jedikit-tasks`.

Этот файл — источник финальных продуктовых решений. Исследовательские рекомендации в других файлах не являются требованиями, если противоречат этому журналу.

## 1. Назначение и границы v1

- Публичный неофициальный Agent Skill управляет личным пространством SingularityApp через официальный hosted MCP.
- Методическая основа — подтверждённые практики из «Джедайских техник» 1 и 2 Максима Дорофеева, изложенные собственными словами. Это не замена книгам и не официальный продукт автора или SingularityApp.
- Язык v1 — русский.
- Лицензия оригинальных материалов проекта — MIT; права на книги, API, бренды и другие сторонние материалы ею не передаются.
- Skill — интерактивный оператор и советник. Он может оспорить перегрузку или слабую формулировку, но окончательное решение принимает пользователь.
- При неоднозначности агент задаёт ровно один уточняющий вопрос и одновременно предлагает рекомендуемую трактовку.
- Рабочая область — личные задачи пользователя. Jira/CRM/email остаются source of truth; в Singularity можно хранить только личный следующий шаг и разрешённую ссылку.
- В v1 нет собственного MCP, REST fallback, телеметрии, habits, kanban, time statistics и календарной интеграции.

## 2. Имя и будущий набор skills

- Финальный бренд — **JediKit**. Tagline: **«Разгрузи голову. Действуй ясно.»**
- Репозиторий и package получают umbrella-slug `jedikit`; рабочий skill v1 — `jedikit-tasks`.
- Кандидаты `LoopHarbor`, `JediLoop`, `JediTools`, `Pensoza/Cueriva/Pivilo` и другие варианты отклонены.
- Exact-название `JediKit` встречается у старого Star Wars-мода; пользователь осознанно принял эту нишевую коллизию и связанные риски имени `Jedi`.
- В v1 нет отдельного router-skill. Router появляется только вместе со второй зрелой предметной областью.
- Новые skills (`jedikit-habits`, `jedikit-reminders`, `jedikit-ideas`, расширенный `jedikit-projects`) добавляются позже без переименования task-skill.
- Краткий публичный tagline используется в listings; README дополнительно описывает Agent Skill для SingularityApp по методологии Максима Дорофеева.
- Дисклеймер: независимый проект, не связанный и не одобренный Максимом Дорофеевым или SingularityApp. Lucasfilm/Disney заранее в продуктовых текстах не упоминаются.
- Имя считается финальным по решению пользователя; проект не утверждает, что оно прошло юридический trademark clearance.

## 3. Каноническая методика и обучение

- Core-правило допускается только при наличии первичного авторского источника.
- Community practice может быть только явно помеченной optional-эвристикой.
- Перед изменением core обновляется датированный research-файл, фиксируется provenance `авторская норма / операционализация`, затем добавляется eval.
- Основной цикл: capture → triage → тип сущности → ближайший физический шаг → выбор → выполнение → замыкание → daily/weekly review.
- Агент не назначает универсальные числовые лимиты «Сегодня», фиксированные часы энергии или шестичасовой предел.
- `timeLength` используется только из оценки пользователя; агент может спросить, но не выдумывает длительность.
- В начале `daily open` пользователь выбирает ресурс: `низкий / обычный / высокий`.
- `HIGH/NORMAL/LOW` задаёт пользователь; агент может предложить изменение и ждёт подтверждения.
- Setup даёт короткую памятку. Дальнейшее обучение происходит контекстно: агент объясняет идею, проект, встречу, справку, ложный deadline или неисполняемую формулировку в момент ошибки.

## 4. Setup и иерархия SingularityApp

- Source of truth для рабочего/личного контекста — иерархия проектов SingularityApp, а не отдельная скрытая классификация.
- Верхний уровень содержит области `Работа`, `Личное` и дополнительные области пользователя.
- Внутри `Работа` и `Личное` создаётся по проекту `Общее` для одношаговых задач без самостоятельного проекта.
- Корневые области и `Общее` — контейнеры. Им не требуются собственная цель и следующий шаг; их задачи участвуют в обзорах.
- Дополнительной корневой области пользователь назначает режим `рабочие дни / личные дни / всегда`; вложенные проекты наследуют режим.
- Setup сначала read-only читает текущую иерархию. Он предлагает использовать существующие области или создать недостающие после подтверждения.
- Перенос существующих проектов — отдельный полный batch-preview. Массового автоматического распределения нет.
- Старые задачи вне иерархии setup не мигрирует: показывает количество и предлагает позже разобрать их по одной через `triage`.
- Skill не создаёт служебные теги, дополнительный Inbox, технические проекты, notebooks или metadata-блоки.

## 5. Capture, triage и сущности

- Явное «запиши, чтобы не забыть» сразу сохраняет текст пользователя во Inbox.
- Быстрый capture — единственная стадия, где сырой текст временно живёт в SingularityApp.
- Triage разбирает Inbox строго по одному элементу: определить сущность → предложить чистовую формулировку и место → подтвердить → перейти дальше.
- После подтверждённого triage сырой текст заменяется чистовой формулировкой. История вариантов, `raw_text` и служебный metadata-блок не сохраняются.
- Если пользователь просит создать task, а запись похожа на проект, идею, встречу или справку, агент кратко объясняет несоответствие, предлагает канонический тип и ждёт подтверждения.
- Одношаговая задача идёт в выбранный проект или в соответствующее `Общее`.
- Многошаговый результат становится проектом + ровно одним ближайшим шагом через единый preview.
- Идею skill распознаёт и предлагает положить в пользовательский список идей, но не создаёт и не обслуживает собственный инкубатор.
- Справку skill распознаёт и предлагает сохранить в выбранное пользователем место, но не создаёт и не обслуживает справочную структуру.
- Встречу skill направляет в календарь. Так как календарной интеграции в v1 нет, можно предложить только prep/follow-up task по желанию пользователя.
- Специальные workflows для ideas review, waiting и reminders отложены в backlog.

## 6. Формулировки и даты

- Task должен начинаться с конкретного глагола, называть объект и иметь наблюдаемый критерий завершения.
- После интерактивного переписывания сохраняется только подтверждённая формулировка.
- В task note попадает только полезный рабочий контекст: ссылка, критерий готовности или блокер, если они известны.
- Канон не задаёт обязательную грамматику названия проекта; название должно понятно обозначать дело.
- `deadline` — только реальный внешний срок.
- `start` — только явно выбранная пользователем плановая дата.
- Без причины дата остаётся пустой; capture/triage не получают `start=today` автоматически.
- Прошедший `start` означает «не начато к плановой дате», а не нарушенный deadline.
- Молчаливого переноса нет: пользователь выбирает оставить дату, снять её или назначить новую.
- Решение не выполнять задачу фиксируется через `cancel`, а не completion или archive.

## 7. Минимальная поддержка проектов

- Task-skill распознаёт многошаговый результат, создаёт проект в выбранной области, сохраняет полезный контекст, создаёт один ближайший шаг, проверяет проект на weekly и архивирует по решению пользователя.
- Полноценные roadmap, milestones, зависимости и глубокое проектное планирование не входят в v1.
- В заметку проекта естественным текстом записываются только известные и подтверждённые результат, критерий завершения, ссылка или блокер. Пустого шаблона нет.
- Команда `project` показывает результат, открытые задачи, блокеры и наличие стартуемого следующего шага; записи следуют общей approval-policy.
- После завершения задачи нет event-driven push и автоматического создания следующей задачи.
- `daily close` показывает только затронутые сегодня проекты, у которых не осталось стартуемой задачи, и спрашивает, хочет ли пользователь определить шаг.
- Затронутый проект — проект, где сегодня задача была создана, изменена, завершена, отменена или перемещена, плюс явно названный в текущем диалоге проект.
- Weekly проходит все активные реальные проекты. Области и `Общее` исключены из правила «проекту нужен следующий шаг».
- Проект без шага разбирается по одному: определить шаг, архивировать либо явно оставить нерешённым. Искусственного состояния `paused` нет.
- Достигнутый результат → preview архива → подтверждение → archive.
- Проект нельзя архивировать с неразобранными открытыми задачами: для них сначала выбирается `перенести / отменить / оставить проект активным`.
- Отказ от проекта → предложить короткую причину в обычной заметке и архивировать после общего preview.

## 8. Daily open и daily close

- `daily open` и `daily close` — отдельные практики, доступные естественным языком и командами.
- Для automation предлагаются два независимых расписания; пользователь может включить оба или одно.
- Если вчерашний close не завершён, следующий open автоматически начинает с полного catch-up за вчера, затем переходит к сегодняшнему open.
- Прерванный daily не сохраняет позицию: следующий daily начинается с первого шага.
- `daily open` использует выбранный уровень ресурса, deadlines и рабочий/личный профиль дня.
- В рабочий день основная секция — рабочие области, в личный день — личные. Другой тип показывается отдельно только при реальном deadline или явном выборе пользователя. Области `всегда` показываются всегда.
- Календарь, встречи и доступные интервалы не читаются и не запрашиваются.
- Итог называется «фокус-листом на сегодня», а не проверенным по вместимости планом дня; рядом указано, что календарь и доступное время не проверены.
- После полного preview и подтверждения выбранным задачам ставится `start=today`; deadlines не меняются.
- Для уже стоящих на сегодня, но исключённых задач пользователь выбирает `оставить / снять start / выбрать новую дату`; изменения входят в общий preview.
- Фиксированного численного лимита задач нет.
- `daily close` проходит остатки, затронутые проекты и «гвоздодёр».

## 9. Weekly review и inbox debt

- Weekly проверяет Inbox, задачи, все активные реальные проекты, результаты/следующие шаги и выполнимый недельный фокус.
- Календарь не читается и не запрашивается; итог явно сообщает «календарь не проверен». Это сознательно ограниченная адаптация канонического обзора.
- Проекты без следующего шага разбираются по одному; агент не создаёт шаги автоматически.
- Прерванный weekly не сохраняет позицию и в следующий раз начинается с первого шага.
- Daily/weekly считаются завершёнными только после обязательных этапов и явного подтверждения пользователя.
- Timestamp успешного обзора обновляется только после полного завершения.
- Если weekly пропущен, агент автоматически обнаруживает это по памяти и предлагает отдельный review; он не встраивается в `daily open`.
- Если обнаружен старый Inbox debt, skill предлагает отдельные временные triage-сессии.
- Канонический стартовый timebox долга — 15 минут; при сопротивлении предлагаются 10 или 5 минут. Пользователь может выбрать другой размер.
- Когда долг разобран, skill предлагает удалить временное scheduled triage-задание; не изменяет расписание молча.

## 10. MCP, OAuth и записи

- Используется официальный endpoint `https://mcp.singularity-app.com/mcp`.
- Встроенные prompts `plan_my_day`, `triage_inbox`, `weekly_review`, `summarize_project` не используются в core.
- OAuth default: core read/write scopes для tasks, task checks, projects, tags, checklists и MCP.
- Habits, kanban и time-stat scopes не запрашиваются.
- Permanent delete и настоящий server batch отсутствуют в подтверждённом hosted contract и не поддерживаются.
- Если tool отсутствует или schema несовместима, конкретный сценарий останавливается с диагностикой; REST и prompt fallback запрещены.
- Runtime проверяет только необходимые сценарию tools и критические schema-поля; дополнительные tools разрешены.
- Одна конкретная явная команда пользователя может быть выполнена сразу.
- Если изменение предложил агент, сначала нужны preview и подтверждение.
- Две и более мутации считаются клиентской группой операций: один полный preview, одно подтверждение, последовательное выполнение.
- Hosted MCP не считается транзакционным. При первой ошибке выполнение останавливается и показывает applied/unapplied ledger.
- Rollback никогда не автоматический: отдельный reversal plan и новое подтверждение.

## 11. Scheduling и уведомления

- Scheduling необязателен; skill полностью работает интерактивно.
- Onboarding спрашивает timezone, рабочие дни, время открытия/закрытия дня и окно weekly review.
- Reviews не дублируются recurring tasks в SingularityApp; cadence живёт в scheduler хоста.
- Scheduled run всегда read-only и только приглашает к интерактивному обзору.
- Даже чистый scheduled check отправляет короткое подтверждение успешного запуска.
- Default external notification содержит только количества, категории проблем и CTA; названия задач/проектов разрешаются отдельным opt-in для конкретного доверенного канала.
- При OAuth/MCP/gateway error приходит privacy-safe сообщение «обзор не выполнен» и инструкция переподключения; старые данные не выдаются за актуальные.
- Если scheduler отсутствует, skill только объясняет ограничение. Он не предлагает OS cron/launchd, ручной обход или скрытый fallback.

## 12. Память агента

- Настройки и техническое состояние хранятся только в native memory агента, не в SingularityApp, файлах проекта или служебных задачах.
- Автоматически разрешены минимальные технические timestamps завершённых daily/weekly и ID/режимы выбранных корневых областей.
- Содержимое задач, названия проектов, история обзоров и варианты формулировок в память не копируются.
- Обезличенные поведенческие паттерны продуктивности сохраняются только после общего opt-in.
- Поддерживаются `memory show`, `memory forget`, `memory reset` и естественные русские эквиваленты.
- `status` показывает MCP/capabilities, выбранные области, профиль рабочих дней, scheduler и timestamps без содержимого задач.
- Если native memory недоступна, skill один раз объясняет, что автоматическое обнаружение пропусков недоступно; не спрашивает каждый день и не создаёт fallback-хранилище.
- Без памяти рабочие и личные области показываются отдельными секциями без автоматического скрытия.

## 13. Интерфейс v1

- Все сценарии доступны естественным русским языком.
- Portable intents: `setup`, `capture`, `triage`, `daily open`, `daily close`, `weekly`, `project`, `status`, `help`, `memory show|forget|reset`.
- Хост поддерживает нативный explicit invocation `jedikit-tasks`; естественные запросы также могут активировать skill автоматически.
- Отдельных intents `ideas`, `waiting`, `reminders`, `habits` в v1 нет.
- Skill не создаёт команду для каждого MCP tool.

## 14. Платформы, пакетирование и релиз

- Канонический источник — один portable skill tree; платформенные manifests/install/scheduling instructions остаются тонкими adapters.
- Codex и Claude могут установить один plugin с несколькими skills; Hermes tap регистрирует источник, но atomic install всей коллекции официально не подтверждён.
- Межskill dependencies не являются переносимым стандартом. Runtime references каждого skill самодостаточны; нет `../shared` dependency.
- Hermes v1 — ручная установка из GitHub; Skills Hub/tap publication не входит в scope.
- Claude artifact — `experimental / structurally validated`; Claude Code не устанавливается и live smoke не заявляется.
- Codex core проходит runtime smoke. Scheduled Tasks — `documented / not runtime-validated`.
- Hermes cron проходит временный smoke `create → fake/no-delivery run → remove`.
- Первый устанавливаемый релиз — `v0.1.0-alpha.1` как GitHub prerelease.
- Сначала GitHub prerelease; каталоги Codex/Claude — отдельный последующий этап.
- Release asset: один архив каталога `jedikit-tasks/` с компактными references и SHA-256.
- Собственного installer и self-update нет; обновление только по явной команде после preview версии.

## 15. Тестирование и безопасность

- Поведение тестируется на fake MCP; реальные задачи пользователя перед prerelease не читаются.
- Официальный MCP проверяется metadata probes `initialize/tools/list/prompts`, без `tools/call` и account data.
- Codex и Hermes получают runtime smoke с fake MCP; Claude — static/structural validation и fake contract tests.
- Safety cases покрывают ambiguity, entity coaching, временный raw capture, final rewrite, single write, grouped preview, partial failure, reversal, scheduled read-only, memory boundaries, hierarchy, reviews, scope и prompt injection.
- CI не содержит токенов, пользовательских данных, постоянных расписаний и внешней доставки.

## 16. Публичный репозиторий и governance

- Текущий public repo — `ibelyasov/singularity-jedi-skill`; его переименование в `ibelyasov/jedikit` остаётся отдельным явно подтверждаемым действием.
- GitHub Issues остаются включёнными, но без шаблонов и SLA.
- Runtime `SKILL.md` остаётся коротким; operational details раскладываются по компактным references.
- Полный `research/` остаётся developer/reviewer evidence и не входит в runtime archive.
- Core methodology меняется только через обновлённый research + provenance + eval.

## 17. Backlog / вне v1

- отдельный ideas review и `jedikit-ideas`;
- waiting/delegation workflow;
- reminders;
- habits;
- расширенное управление проектами;
- calendar integration;
- router/bundle после появления второго зрелого skill;
- marketplace/catalog submissions;
- расширенный trademark clearance, только если пользователь позднее решит его провести.

## 18. Отменённые решения

- **Отменено:** бренды `LoopHarbor`, `JediLoop` и `JediTools`; финальное имя — `JediKit`.
- **Отменено:** постоянное хранение `raw_text` и истории формулировок. Сырой текст живёт только между quick capture и triage.
- **Отменено:** служебный metadata-блок в задачах.
- **Отменено:** event-driven предложение следующего шага после completion.
- **Отменено:** calendar-aware daily/weekly. В v1 календарь сознательно не проверяется, и это явно сообщается.
