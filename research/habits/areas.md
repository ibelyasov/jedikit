# Области Habitify: организация, научные основания и границы

**Проверено:** 2026-10-06.\
**Вопрос:** зачем агенту предлагать Areas и что позволяет такое предложение
обосновать, сохранив одну привычку за раз, эксперимент и Safety?

Это исследовательское основание сценария
[areas.md](../../skills/jedikit-habits/references/areas.md); исполняемые инструкции
находятся в скилле. Различаются **академические выводы**, **заявления Habitify**
и **вывод проекта**. Целевой поиск первичных публикаций и официальной документации
не является систематическим обзором. Даты возле ссылок обозначают фактический
доступ, а не дату публикации. ID и библиография — в [реестре](../sources.md);
объём текущего чтения — в §2 и §5. Реестр сохраняет также прежние read scopes.

## 1. Что документирует Habitify

**Заявление vendor.** Area — пользовательская группа привычек по жизненным
аспектам и приоритетам. В приложении можно выбрать название, иконку, цвет и
включаемые привычки; затем изменять эти настройки и состав.
[HABITIFY-UI-AREAS](https://intercom.help/habitify-app/en/articles/6113636-create-manage-custom-areas),
доступ 2026-10-06.

В Journal названия Custom Areas видны на Area Bar; выбор области фильтрует
дневной список. Панель можно скрыть. Это документированное поведение интерфейса,
не проверка установленного приложения.
[HABITIFY-UI-JOURNAL](https://intercom.help/habitify-app/en/articles/12520095-understanding-your-journal-view-ios-android-apps),
доступ 2026-10-06.

Time of Day выделяет временные блоки и может автоматически выбирать актуальный.
Это отдельный способ организации списка. Он не заменяет напоминание или
конкретный сигнал действия; одинаковое расположение в Area Bar не делает
Custom Area и Time of Day одним объектом.
[HABITIFY-UI-TIME-OF-DAY](https://intercom.help/habitify-app/en/articles/7990118-manage-the-time-of-day),
доступ 2026-10-06; различие со сигналом — вывод проекта на основе §2.

### REST v2 и инструменты хоста

Источник каждой строки таблицы — официальный
[HABITIFY-OPENAPI](https://api-docs.habitify.me/openapi/v2/openapi-bundled.yaml),
доступ **2026-10-06**; номера строк относятся к snapshot с SHA256 из §5.
Имена инструментов хоста даны владельцем в задаче; их фактические schemas
и выполнение здесь не проверялись.

| Инструмент / объект | Документированный REST-контракт |
| --- | --- |
| Area | Properties: `id`, `name`, `createdAt`, `colorHex`, `icon`; последние два nullable. Цвет описан как hex; pattern не задан. Строки 1014–1042. |
| `list-areas` → GET /areas | Список всех областей, `data: Area[]`; query pagination не описана. 4230–4276. |
| `create-area` → POST /areas | Обязателен `name`, необязательны `colorHex` и `icon`; ответ 201. 4280–4336. |
| `get-area` → GET /areas/{areaId} | Область по ID, ответ 200 или 404. 4343–4396. |
| `update-area` → PUT /areas/{areaId} | Изменяются переданные `name`, `colorHex`, `icon`. 4397–4469. |
| `delete-area` → DELETE /areas/{areaId} | Область удаляется навсегда; привычки отвязываются от неё и **не удаляются**. Успех 204. 4470–4490. |
| `create-habit` → POST /habits | `areaIds` — необязательный массив ID назначаемых областей. 1762–1766. |
| `update-habit` → PUT /habits/{habitId} | `areaIds` **заменяет** назначения; описание vendor заявляет сохранение непереданных полей, runtime не проверен. 3185–3186, 3295–3299. |
| `list-habits` → GET /habits | Фильтр `areaId`; отдельно `timeOfDay` и `archived`; пагинация `limit`/`offset`. 1090–1130. |

**Уточнение исходного контекста.** В текущем API поле называется `colorHex`,
а не `color`; есть также `icon`. Вход назначения временных блоков —
`timeOfDayIds`, фильтр списка — `timeOfDay`. Схема Area включает
`description` в required, но не определяет его в properties: это дефект
декларации, не разрешение отправлять выдуманное поле.
[HABITIFY-OPENAPI](https://api-docs.habitify.me/openapi/v2/openapi-bundled.yaml),
строки 1017–1042, 3300–3304; доступ 2026-10-06.

Vendor также представляет Area Overviews как способ увидеть распределение
времени между сферами и заметить дисбаланс. Это продуктовый тезис о Progress View,
не доказательство психологического баланса или пользы областей.
[HABITIFY-PROGRESS-AREAS](https://feedback.habitify.me/changelog/all-new-progress-view-2),
публикация 2026-05-26, доступ 2026-10-06.

## 3. Практический смысл для JediKit

**Вывод проекта, не доказанный эффект.** Область может упростить поиск и обзор
нескольких уже имеющихся привычек по понятному пользователю признаку. Возможная
польза — удобство конкретного фильтра; её оценивает пользователь. Основание:
[документированный фильтр](https://intercom.help/habitify-app/en/articles/12520095-understanding-your-journal-view-ios-android-apps),
доступ 2026-10-06. Клиническая польза и более быстрое формирование из этого не следуют.

Проактивное предложение уместно при появлении второй или следующей привычки
похожего назначения, при setup/status или обзоре, если пользователь ищет
несколько связанных привычек либо жалуется на длинный список. Число «две» —
эвристика проекта, не научный порог. Сначала можно предложить использовать
существующую область: «Эти две привычки удобно видеть вместе. Добавить их
в выбранную область?» Привычки для Preview перечисляются явно, без выбора
всего аккаунта по одному признаку.

Для одной привычки без запроса на группировку отдельная область обычно не нужна.
Не нужны заранее заполненное «колесо жизни», обязательные цвета или новая
классификация на каждом обзоре. Если вопрос только о времени дня, сначала
рассматривается уже имеющийся Time of Day. Неравное число привычек или пустая
область не устанавливают жизненный дисбаланс. Это ограничения проекта,
согласующиеся с косвенностью данных §2; они не являются измерением нагрузки.

Смысловая сфера и сигнал действия различаются: «Учёба» отвечает, к чему относится
поведение, «после завтрака читаю одну страницу» — когда начать его проверку.
На обзоре обсуждаются реальные пересечения времени и возможностей,
взаимная поддержка или конфликт действий, а не только названия Areas.
Основания: Wood–Neal, Gollwitzer–Brandstätter, Riediger–Freund в §2,
доступ 2026-10-06.

Группировка уже существующих привычек — организационная группа операций,
а не группа новых экспериментов. Область не повод запускать несколько поведений,
менять их планы или добавлять отметки. Одна привычка за раз, одна гипотеза
и изменение одной вещи сохраняются; наличие нескольких привычек в аккаунте
этому не противоречит. Основания проекта:
[CONTEXT](../../CONTEXT.md), [experiments.md](../../skills/jedikit-habits/references/experiments.md),
[areas.md](../../skills/jedikit-habits/references/areas.md),
прочитаны 2026-10-06.

## 4. Риски и границы операций

| Риск | Что известно и как ограничить предложение |
| --- | --- |
| Удаление области | По API привычки сохраняются, удаляется область и связь с ней. До предложения нужен полный список затронутых привычек: все страницы, активные и архивные. Для Read-back после удаления — отсутствие области и сохранность привычек/остальных назначений. Не обещать восстановление Area с прежним ID: такой контракт не найден. [OpenAPI](https://api-docs.habitify.me/openapi/v2/openapi-bundled.yaml), доступ 2026-10-06; порядок чтений — вывод проекта. |
| Замена `areaIds` | При добавлении области передача только нового ID может убрать прежние назначения. Нужны свежий GET выбранной привычки, точный полный будущий набор и сверка `areas[].id` после записи. Очищение через `[]` следует из replacement и допустимости пустого массива по схеме, но отдельное обещание очищения и runtime не проверены; `null` не объявлен допустимым. [OpenAPI](https://api-docs.habitify.me/openapi/v2/openapi-bundled.yaml), доступ 2026-10-06; защитные действия — вывод проекта. |
| Неполный список / смешение объектов | GET habits пагинируется и отдельно фильтрует archived и timeOfDay. Один дневной список не доказывает полноту назначений. Область Habitify не наследует дерево, режимы и проекты SingularityApp из CONTEXT. [OpenAPI](https://api-docs.habitify.me/openapi/v2/openapi-bundled.yaml) и [CONTEXT](../../CONTEXT.md), прочитаны 2026-10-06. |
| Приватность названий | Custom Area names видны в приложении. **Вывод именно Area names в уведомлениях не документирован в проверенных источниках; неизвестен.** Это не гарантия их скрытия. При чувствительном содержании предложить нейтральное имя по предпочтению пользователя; не выводить диагноз или приватный смысл из привычек. [Journal](https://intercom.help/habitify-app/en/articles/12520095-understanding-your-journal-view-ios-android-apps), [Areas](https://intercom.help/habitify-app/en/articles/6113636-create-manage-custom-areas), [Reminders](https://intercom.help/habitify-app/en/articles/12396874-good-habit-setting-reminders), доступ 2026-10-06. |
| Проактивность превращается в нагрузку | Предложение не разрешает запись. Дополнительная классификация не должна вытеснять план эксперимента; при отсутствии пользы или после отказа её откладывают. Внешние уведомления хоста содержат количества без названий, если отдельное согласие на названия не дано. Это политика проекта, а не результат испытания Areas. [areas.md](../../skills/jedikit-habits/references/areas.md), [ADR 0003](../../docs/adr/0003-no-unattended-writes.md), прочитаны 2026-10-06. |

Публичное описание PUT заявляет сохранение непереданных полей: это vendor statement,
а не проверенное поведение адаптера. В
[habitify-tools.md](../../skills/jedikit-habits/references/habitify-tools.md)
сохранён guard полной writable-конфигурации и её Read-back после записи.
Обязательного ручного runtime-гейта нет
([ADR 0005](../../docs/adr/0005-one-source-host-connections.md)).
[OpenAPI](https://api-docs.habitify.me/openapi/v2/openapi-bundled.yaml), строки
3185–3186; доступ 2026-10-06.

## 5. Открытые вопросы и метаданные

- Не установлены дополнительный эффект Areas, оптимальное количество,
  названия/цвета или универсальная экономия внимания; прямой сравнительный

## Рекомендации для скилла

Ниже **правила проекта** из
[сценария скилла](../../skills/jedikit-habits/references/areas.md), а не научная доза.
Основания — §1–4 (первичные ссылки, доступ 2026-10-06),
[CONTEXT](../../CONTEXT.md), [operation-policy.md](../../skills/jedikit-habits/references/operation-policy.md)
и [experiments.md](../../skills/jedikit-habits/references/experiments.md), прочитаны 2026-10-06.

1. **Объясняй назначение одним предложением:** область помогает видеть выбранные
   привычки вместе. Не обещай ускоренное формирование, снижение нагрузки,
   здоровье или «баланс жизни» благодаря папке либо цвету.
2. **Предлагай область проактивно при наблюдаемой потребности:** вторая или
   следующая привычка сходного назначения, поиск связанных привычек, длинный
   список при setup/status или обзоре. Назови конкретную пользу и предложи
   один небольшой вариант; число привычек не делай обязательным порогом.
3. **Пропускай лишнюю организацию:** для одной привычки без запроса область
   обычно не нужна; не заполняй все сферы, не назначай квоты и не повторяй
   отклонённое предложение без новой потребности. Для вопроса только о времени
   дня сначала рассматривай Time of Day.
4. **Сначала используй существующую структуру:** прочитай области и явно
   выбранные привычки, предложи подходящую имеющуюся область до создания новой.
   Не создавай дубль и не делай скрытого назначения по похожим названиям.
5. **Сохраняй один эксперимент:** группировка существующих привычек не
   разрешает запуск нескольких новых поведений, изменение планов или отметки.
   На обзоре выбранного эксперимента меняй одну вещь; область не заменяет
   реальный сигнал, if–then или Safety-стоп.
6. **Согласуй названия и приватность:** предложи нейтральное имя вроде
   «Личное» или «Учёба» с учётом известного предпочтения пользователя.
   Назови видимость в приложении и неизвестность Area names в уведомлениях;
   не включай диагноз или чувствительную интерпретацию без запроса,
   не переименовывай существующие объекты сам. Цвет и иконка необязательны.
7. **Для своего предложения покажи Preview и дождись подтверждения:** точные
   области/areaId, привычки/habitId, старые → новые имена и наборы назначений,
   поля, последствия и порядок записей. При создании ID берётся из ответа;
   зависимое назначение входит в тот же Preview. Существенное изменение
   Preview требует нового согласия.
8. **Явную одиночную команду выполняй без повторного согласия:** при
   однозначном объекте и действии прочитай исходное состояние, выполни только
   выбранную запись и сделай Read-back. Не добавляй соседнюю группировку;
   при неоднозначности задай один вопрос с рекомендуемой трактовкой.
9. **Не теряй назначения при PUT:** получи свежий полный набор областей
   привычки, вычисли согласованный будущий набор с сохранением остальных
   назначений и передай весь `areaIds`. Не отправляй один новый ID как
   «добавление» и не используй `[]`/`null` для неоговорённого очищения;
   сравни полный набор `areas[].id` при Read-back.
10. **Группу операций веди последовательно:** один Preview, одно подтверждение,
    запись → Read-back для каждого явно выбранного объекта; стоп при первой
    ошибке записи или чтения. Отчёт: applied / unverified / unapplied.
    Без bulk, «всех привычек», слепых повторов и автоматического отката.
11. **Удаление области предлагай отдельно по смыслу пользователя:** пустота,
    возраст или похожесть названий сами по себе его не разрешают. Прочитай
    все страницы связанных активных и архивных привычек, поясни permanent
    delete области и сохранение привычек с потерей этой связи; не обещай undo.
    После удаления проверь отсутствие области и состояние затронутых привычек.
12. **В фоне только читай и собирай предложения:** не создавай, не назначай,
    не переименовывай и не удаляй области. Во внешнем уведомлении хоста —
    количества без названий, если отдельного согласия на названия нет.
    При сигналах клинического риска применяй Safety-стоп; классификация
    не заменяет помощь человеку.
