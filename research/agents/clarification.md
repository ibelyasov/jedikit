# Неполный ввод: уточнения и grilling

Дата исследования и доступа к внешним источникам: **2026-10-07**. Досье различает научные результаты, авторские методы, документацию хостов и продуктовую интерпретацию. Согласованные продуктовые решения изложены в разделе «Применение в JediKit» отдельно от внешних оснований; это не свидетельство реализации в скиллах.

Для операций задач, привычек и личного календаря обязательные данные определяет доменный скилл. Общий принцип — использовать известное, собрать все блокирующие пробелы одним сообщением и не спрашивать необязательное. Глубокое уточнение намерения выполняется через внешний `grill-me`; его отсутствие нужно назвать и рекомендовать установку средствами хоста. Механика совместной загрузки рассмотрена в [досье о композиции](skill-composition.md), выбранный календарный контракт — в [Google Calendar](../providers/google-calendar.md).

Источники обозначены ID в [едином реестре](../sources.md). Локальные наблюдения исходного исследования относятся к JediKit commit `43fc19e8f2d175195b8a27e92646941e2252efbb`; они не подменяют действующие правила. Классы оснований — по [исследовательской библиотеке](../README.md): source inspection, vendor guidance и результат эксперимента не взаимозаменяемы.

## Что именно считать недостающим

Ниже — аналитическое разделение, а не новая schema JediKit.

| Вид пробела | Пример | Как установить |
| --- | --- | --- |
| Намерение или объект | Записать мысль, назначить встречу или поставить задачу позвонить стоматологу? Какая из двух одноимённых привычек? | Текущий запрос, контекст разговора, адресные list/get; при оставшейся неоднозначности — вопрос. |
| Технически обязательный аргумент | `name`/`type` для `create-habit`; поддержанный runtime tool требует дату | Контракт tools.json и текущая inputSchema хоста; неизвестная schema не заменяется вопросом о выдуманном поле. |
| Смысл, необходимый сценарию | Для Triage — стартуемое действие; для Design — критерий отметки; для timed event — действительное время | Правила доменного скилла и ответ пользователя; техническое принятие API не доказывает достаточность смысла. |
| Необязательное обогащение | Приоритет задачи, цвет привычки, адрес уже понятной встречи | Пропустить, если не выбрано и не влияет на разрешённую операцию. Не превращать весь API в анкету. |
| Разрешение | Можно ли создать привычку **и** заметку; заменить полный текст плана | Применить политику явных команд и предложений агента; отдельно — host approval, если хост его требует. Ответ о времени сам по себе не подтверждает ещё не показанный набор изменений, собранный агентом. |

## Научные основания: когда и о чём спрашивать

Это целевая подборка первичных публикаций, **не систематический обзор**. Полные тексты доступны; фактически прочитанные разделы указаны в записях реестра. Abstract-only источники не использованы. Статьи описывают разные задачи и поколения систем: их нельзя объединить в один измеренный эффект для JediKit. [CL-SCI-01](../sources.md)–[CL-SCI-07](../sources.md).

| Работа и класс основания | Что поддерживает | Чего не доказывает |
| --- | --- | --- |
| Horvitz, CHI 1999, теоретическая модель mixed initiative | Сопоставлять ожидаемую полезность действия, бездействия и диалога с ценой ошибки/прерывания; есть пример календарного помощника LookOut | Численный confidence threshold или оптимальное число вопросов; это не пользовательский trial. [CL-SCI-01](../sources.md). |
| Singh et al., JAIR 2002, эксперимент NJFun, spoken task-oriented dialogue | Сбор activity/location/time и выбор initiative/confirmation; можно принимать сразу несколько сведений из ответа, даже если запросили одно | Превосходство этой политики в LLM-чатах. Binary completion вырос с 52% до 64%, но `p=0.059`: именно этот исход нельзя назвать значимым при 0.05. [CL-SCI-02](../sources.md). |
| Rao & Daumé III, ACL 2018, offline ranking вопросов | Expected Value of Perfect Information: оценивать вопрос через полезность возможных ответов; очень узкий yes/no-вопрос может не дать нужной информации | Успешную provider write или универсальную пользу рекомендуемого ответа. Candidate ranking на StackExchange не является UX-тестом наших скиллов. [CL-SCI-03](../sources.md). |
| Aliannejadi et al., SIGIR 2019, Qulac, offline conversational search | Хороший вопрос может уточнить информационную потребность; поддерживаются последовательные вопросы | Утверждение «один лучше пачки»: эффект oracle по поисковой метрике не является сравнением форматов диалога; реальные разговоры двух участников не собирались. [CL-SCI-04](../sources.md). |
| Kim et al., ASRU 2021, industrial offline modelling | Отделять обнаруженную ambiguity от необходимости вопроса: некоторые неоднозначности не ухудшают результат | Разрешение угадывать важный параметр записи. Labels dissatisfaction — модельный proxy по взаимодействиям, не прямые оценки каждого пользователя. [CL-SCI-05](../sources.md). |
| Zhang et al., ACL 2024, CLAMBER, LLM benchmark | Различать неизвестную сущность, противоречие, lexical/semantic ambiguity, missing who/when/where/what; detection и качественный вопрос — отдельные задачи | Качество нынешних моделей/хостов владельца; авторы отмечают чувствительность к prompts. Это не готовая schema задач/привычек. [CL-SCI-06](../sources.md). |
| Kim, Lee & Gweon, CHI 2019, рандомизированный 2×2 HCI-эксперимент | Смена web-grid на чат может менять качество ответов и время заполнения; в изученной выборке чат давал более differentiated answers и занимал больше времени | Чистый эффект одного вопроса против пачки: одновременно менялись платформа, представление и взаимодействие; выборка — корейские подростки. [CL-SCI-07](../sources.md). |

В NJFun тестирование включало 124 диалога против 311 training dialogues; указанный результат относится к binary completion в этой системе, не к точности уточнения наших сущностей. Это важная граница единственного приведённого здесь численного эффекта. [CL-SCI-02](../sources.md).

**Slot filling** в этом контексте — удерживать уже известные значения нужных сценарию атрибутов и выяснять оставшиеся, сохраняя возможность принять несколько атрибутов из свободного ответа. Это наша переносимая интерпретация task-oriented dialogue, не предложение вводить отдельный код или хранилище. Отсутствующее значение, несколько кандидатов и противоречие требуют разных вопросов. [CL-SCI-02](../sources.md), [CL-SCI-06](../sources.md).

**Один вопрос или пачка.** Прямого контролируемого сравнения этих двух форматов для коротких записей в LLM-агентах личной продуктивности в подборке не найдено. Qulac и исследование chatbot survey не устанавливают научный optimum для JediKit. [CL-SCI-02](../sources.md), [CL-SCI-04](../sources.md), [CL-SCI-07](../sources.md). Согласованное продуктовое решение независимо от этого: все блокирующие пробелы собираются одним сообщением, по пункту на пробел; известное и необязательное не спрашивается. Ограничения «ровно один» или «не больше 2–3 полей» в этом решении нет. Новый пробел, который станет известен только после ответа, выясняется после него; уже сообщённое повторно не спрашивается. Это продуктовая политика, а не установленное экспериментами превосходство формата.

**Рекомендованный ответ и default.** Подборка не устанавливает, что recommendation, preselection или `yes` для согласия универсально улучшают точность/скорость. В `grilling` рекомендация — авторский приём; в хостах она может быть UI-конвенцией. Наше предложение: рекомендовать обоснованный **выбор**, а неизвестный **факт** спрашивать свободно. Возможное наведение на неверное значение — риск дизайна, не измеренный здесь психологический эффект. [CL-MP-01](../sources.md), [CL-SCI-03](../sources.md).

## Чем хосты могут задавать вопросы

Ниже только **факт наличия интерфейса** по официальной документации/source. Прочитанные локальные версии: Claude Code 2.1.292, Codex 0.160.1; Hermes CLI в PATH не найден. Это не означает отсутствия Hermes у владельца на другом хосте. Документация меняется независимо от этих версий; UI, callbacks и account availability не запускались. [CL-HOST-09](../sources.md).

Agent SDK различает clarification и permission, хотя использует общий callback. [CL-HOST-01](../sources.md), [CL-HOST-02](../sources.md). | Семантику вопроса, варианты и ожидание ответа; не обязательное имя tool или обещание наличия кнопок в каждой поверхности. |

**Version drift Hermes:** текущая reference описывает `responses/outcome` и statuses answered/skipped/unanswered, тогда как прочитанный release source возвращает `responses`, возможные `timed_out`/`notice`. Это разные версии контракта; точную форму надо брать из хоста, а не копировать из текущей веб-страницы. Для переносимого текста достаточно правила «пропуск/timeout не является ответом или согласием на зависимую запись». Последнее — наша политика-кандидат, согласующаяся с ожиданием ответа в JediKit. [CL-HOST-03](../sources.md), [CL-HOST-04](../sources.md), [CL-JK-01](../sources.md).

**Вопрос, продуктовое подтверждение и host approval различаются по назначению.** Hermes security описывает отдельный dangerous-command approval с deny при timeout. В Codex connector approval может использовать тот же wire method `tool/requestUserInput`, а в Claude SDK callbacks общие; значит, нельзя обещать всегда разные API-каналы. Кнопка разрешения tool call не сообщает дату встречи и не заменяет требуемый Preview. [CL-HOST-02](../sources.md), [CL-HOST-05](../sources.md), [CL-HOST-08](../sources.md), [CL-JK-01](../sources.md).

Переносимая часть инструкции — нужный смысл вопроса, известные значения, доступные ответы, свободное уточнение, ожидание и действие при отсутствии ответа. Имена `AskUserQuestion`, `clarify`, `request_user_input`, UI limits и result fields относятся к хостам; добавлять их как обязательные инструменты `tools.json` на основании этого исследования не предлагается. Это продуктовая интерпретация перечисленных контрактов, без MCP-деклараций и нового кода.

## Применение в JediKit

Согласованный продуктовый контракт разделяет два вида доспроса: поля операции уточняет доменный скилл, глубокое намерение — внешний `grill-me`. Все блокирующие пробелы собираются одним сообщением; известное и необязательное не спрашивается. Рекомендация должна иметь основание и не заменяет неизвестный личный факт. Относительную дату нужно показать в результате, без отдельного переспроса. После интервью доменный скилл применяет свои правила записи.

Согласованная политика подтверждений различает явную полную команду, одиночное предложение агента и собранный агентом набор: первая выполняется сразу, для второго достаточно одной строки и согласия, для набора нужен общий Preview. Явно названные несколько записей выполняются последовательно без Preview, со стопом на первой ошибке и отчётом applied/unapplied. Habitify требует отдельного однострочного подтверждения безвозвратной потери данных. После записи — Read-back; фон только читает. Это продуктовые решения, не экспериментальный вывод из статей.

### Default, вопрос и Preview

| Ситуация | Вариант поведения в рамках текущего контракта |
| --- | --- |
| Значение известно как настройка и применимо | Использовать его без повторного вопроса: например, timezone. При конфликте с текущими словами пользователя уточнить конфликт. Известный timezone не сообщает время приёма. |
| Необязательное поле не выбрано | Пропустить. Для update сохранить текущее значение по guard, а не передать случайный default или empty value. |
| Обязательный факт неизвестен | Спросить. «Во сколько приём?» нельзя заменить предложением «Наверное, 10:00». Отсутствующее время не означает all-day. |
| Есть полезный выбор, но это предложение агента | Показать конкретное значение как предложение с основанием. Если все остальные данные есть, показать одной строкой и получить согласие; для собранного агентом набора использовать общий Preview. |
| Условия уже согласованы и нужен Preview группы | Показать сразу общий точный Preview вместо повторных вопросов по каждому согласованному полю. Незаполненные значения, влияющие на запись, предварительно выяснить; «время уточним» не является готовым Preview выполнения. |
| Ясная одиночная команда, данные достаточны | Выполнить без лишнего подтверждения, кроме прямо предусмотренных исключений Habitify; затем Read-back. |
| Пользователь не знает обязательного факта / не ответил | Не выполнять зависимую запись. Предложить разрешённый меньший результат: сохранить исходный текст по явной просьбе либо вернуться к вопросу позже. Не создавать дополнительный объект автоматически. |

Настройка означает явный выбор пользователя, допустимый для хранения по ADR 0006, а не догадку модели и не неявный default провайдера. Нельзя объявить уже принятым «стоматолог всегда 60 минут»: такой настройки нет в согласованном календарном контракте.

## Непроверенные слои и риски

- Не проверены вызовы скиллов друг из друга, discovery/installed inventory, UI вопросов, callbacks, доступность режимов, реальные timeout/skipped ветки и удержание нескольких полей моделью. Это scope другого исследования либо runtime, а не вывод по docs.
- Не использовались provider accounts, OAuth, ключи, Google Calendar/Habitify/SingularityApp записи и Read-back. Успех статического validator не докажет качество диалога.
- Source pin Matt проверен, но отличается от локальной 1.3.1; exact installed commit и newest upstream не установлены. Mutable snapshots расходились. Hermes current docs и pinned source имеют разную форму результата clarify.
- Комьюнити: Superpowers/GSD/ToB даны с конкретными историческими pins; GSD repo архивирован, ToB clarification-plugin удалён. Spec Kit прочитан на mutable main без доступного pin-to-content. Runtime кейсов и репрезентативность обсуждений не установлены; лицензии новых коллекций не исследованы, их инструкции не включены в пакет.
- Не выполнены полная юридическая оценка, systematic literature review и прямое сравнение архитектур уточнения, 1-vs-batch или recommended answer. Нет научно выведенного универсального лимита вопросов.
- Риски продукта: лишние вопросы и смешение Capture с Triage; выдуманные «рекомендуемые факты»; обязательная сторонняя зависимость; разрастание дерева интервью; смешение ответа, Preview/подтверждения и host approval. Это прогнозы по найденным контрактам, не наблюдённые инциденты.

Досье само по себе не подтверждает runtime или полномочия записи.
