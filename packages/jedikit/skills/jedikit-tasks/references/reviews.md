# Обзоры, память и расписание

Назначение: проводить daily/weekly с правильным охватом, управлять только минимальной native memory и безопасно предлагать host-native расписания.

## Разделы

1. Native memory
2. Daily open
3. Daily close
4. Weekly review
5. Inbox debt
6. Scheduler и status

## 1. Native memory

Разрешённые поля native memory (запись — по политике операций):

- timezone и рабочие дни;
- окна daily open/close и weekly;
- IDs root/`Общее` и режимы roots (`work / personal / always`);
- технические пары `last_daily_close_review_date` +
  `last_daily_close_completed_at` и `last_weekly_review_date` +
  `last_weekly_completed_at` только для полностью и явно
  завершённых обзоров. `*_review_date` — локальная календарная дата в
  сохранённой timezone, которую разобрали; `*_completed_at` — ISO 8601 момент
  фактического завершения с offset. Эти значения не являются review history.

Не храни названия/тексты задач и проектов, raw capture, review history или checkpoint прерванного обзора. Используй только native memory хоста; файлового, Singularity metadata или скрытого fallback нет.

Обезличенные productivity patterns не входят в эту runtime allowlist. Даже при
общем opt-in не изображай их сохранение: сообщи, что текущая реализация хранит
только перечисленные настройки и технические даты. Расширение allowlist требует
отдельного подтверждённого контракта с точными полями.

Legacy memory может содержать только completion timestamp без соответствующего
`*_review_date`. Не выводи дату обзора из момента завершения: close мог
завершиться после полуночи. Назови неопределённость и при необходимости задай
один вопрос о последней фактически разобранной локальной дате. Новую пару
покажи в preview и сохрани только после подтверждения обычной memory write;
старый ключ не очищай и не мигрируй скрыто. Пока дата неизвестна, не объявляй
конкретный обзор пропущенным как доказанный факт.

Timezone, рабочие дни и окна — операционные настройки, а не task content. Setup сохраняет их после общего preview; служебную задачу или setup memo в SingularityApp не создавай.

- `memory show`: показать allowlist выше; legacy task/project content не читать и не выводить.
- `memory forget`: уточнить одну настройку/ID/техническую дату, показать preview ровно этого ключа и удалить только после подтверждения.
- `memory reset`: preview всех присутствующих разрешённых ключей без task/project content, подтверждение, затем последовательная очистка; при первой ошибке остановиться и показать applied/unapplied.

Если native memory или достоверные root modes недоступны, объясни это один раз
за session. В обзоре покажи отдельные видимые секции `Работа`, `Личное` и
`Неклассифицировано`; не угадывай профиль дня и не скрывай секцию по календарю.
Для классификации read-only прочитай `project_list` и восстанови ancestry задач
до видимых root `Работа`/`Личное`; неоднозначные или не входящие в эти roots
задачи покажи в `Неклассифицировано`. Названия не доказывают режим
дополнительного root. Без timestamps нельзя автоматически доказать пропуск
daily/weekly.

Если timezone или weekly window не настроены, не вычисляй дату пропуска
по догадке. Объясни, что автоматическая проверка пока недоступна; настройку
можно согласовать отдельно. Это не мешает явно запрошенному обзору.

## 2. Daily open

1. Если memory доступна, в начале интерактивного запуска проверь пропуски. В
   сохранённой timezone вычисли последнее уже прошедшее weekly window. Weekly
   пропущен, если `last_weekly_completed_at` отсутствует или раньше этого window;
   предложи отдельный review, но не запускай его внутри daily.
   Если не завершён close за вчера, сначала проведи catch-up с
   `review_date=<вчера в сохранённой timezone>`, затем переходи к open сегодня.
2. Спроси ресурс: `низкий / обычный / высокий`. Не выводи его из числа задач.
3. Прочитай `task_list_today(timezone)`, `task_list_overdue(timezone)` и открытые задачи через пагинированный `task_list`; локально проверь все непустые `deadline`, включая будущие. Это намеренно широкое чтение: текущая схема `task_list` не даёт range-query или sparse `fields`, а задача с внешним deadline может не иметь `start`. Не включай removed/archived и recurrence instances, не передавай прочитанный content во внешнюю доставку и не считай прошедший start deadline.
4. При достоверных настройках определи профиль дня по рабочим дням и выбору
   пользователя: work roots в рабочий день, personal roots в личный, `always`
   всегда. Для каждой задачи отдельно: противоположную область включай только
   при её собственном deadline сегодня или явном выборе пользователя. Без
   memory используй видимые секции из §1 без такого фильтра. Будущий deadline
   покажи отдельно и спроси, требует ли он действия сегодня.
5. Покажи **фокус-лист на сегодня** без числового лимита и обязательно скажи: «Календарь и доступное время не проверены».
6. До preview собери решения для обеих групп: выбранным задачам предложи
   `start=today`; для исключённых уже-today получи решение `оставить / снять
   start / новая дата` (саму дату называет пользователь).
7. Покажи один combined preview со всеми selected и excluded tasks, включая
   записи `оставить` как явно неизменяемые. После одного подтверждения выполни
   только перечисленные writes последовательно и сделай read-back каждой
   изменённой task.

Не задавай фиксированные часы, не обещай вместимость и не меняй deadline.

## 3. Daily close

Daily close всегда получает явный `review_date` в локальной timezone. Обычный
close использует сегодня, catch-up — вчера. Completion timestamp записывается
отдельно и не меняет дату обзора.

1. Покажи доступные незавершённые задачи, относящиеся к `review_date`, и спроси
   решение без silent rollover. `task_list_today` описывает текущий Today, а не
   произвольную прошлую дату: для catch-up используй доступные task fields и
   временные границы, но не выдавай текущее состояние за исторический снимок.
2. Проверь реальные проекты, затронутые в интервале локального `review_date`,
   по `task_list(modifiedSince=<начало review_date>)` с локальным отсечением до
   конца дня, если schema возвращает более новые изменения, и проекты из
   текущего диалога. Не сохраняй `touched_project_ids`. Провайдер может не
   хранить достаточную историю перемещений, завершений или прежних значений;
   перечисли недостающие факты и спроси их у пользователя вместо догадки.
3. Контейнеры исключи. Для каждого затронутого проекта проверь результат и стартуемый шаг.
4. Если шага нет, показывай проекты по одному и спрашивай, хочет ли пользователь определить шаг. Не создавай его автоматически.
5. Проведи «гвоздодёр»: попроси пользователя мысленно прокрутить
   `review_date` назад от текущего/вечернего момента к началу дня — места,
   разговоры, сообщения и переключения — и назвать всплывшие мысли или
   обязательства. Каждое названное входящее обрабатывай по capture policy:
   явная просьба записать создаёт raw Inbox item с read-back; без такой просьбы
   покажи найденное и спроси, что сохранить. Это не замена обзора.
6. После всех секций покажи в финальном preview точную
   `last_daily_close_review_date` и правило `last_daily_close_completed_at =
   момент получения подтверждения «завершить»`. Явное завершение подтверждает
   эту запись; после ответа возьми фактический ISO 8601 момент с offset,
   запиши пару и выполни read-back обоих полей без повторного подтверждения.
   Не сохраняй время preview: ответ может прийти после полуночи. При неизвестных фактах явно отличи «обзор
   завершён с указанными ограничениями» от предположения, что история
   восстановлена.

## 4. Weekly review

В начале каждого интерактивного обзора, если memory доступна, вычисли в
сохранённой timezone последнее уже прошедшее weekly window. Если
`last_weekly_completed_at` отсутствует или раньше этого момента, weekly пропущен:
предложи запустить его отдельно. Daily open/close не содержит weekly целиком.
Каждый weekly начинается с первого шага:

1. Inbox и состояние долга разбора.
2. Через `task_list` прочитай незавершённые и отменённые задачи и проверь их поля `start`/`deadline`, включая будущие внешние deadline; отдельно прочитай `task_list_overdue(timezone)`.
3. Все активные реальные проекты, не только затронутые сегодня.
4. Для каждого: наблюдаемый результат и один стартуемый ближайший шаг. Root/`Общее` исключить.
5. Предложить жизнеспособный недельный фокус без числовой квоты.
6. Сказать: «Календарь и доступное время не проверены».
7. После всех секций показать в финальном preview точную
   `last_weekly_review_date` и правило `last_weekly_completed_at = момент
   получения подтверждения завершения`. После явного завершения вычислить
   фактический ISO 8601 момент с offset, записать и прочитать оба поля обратно
   без второго подтверждения. Время preview не подставлять вместо завершения.

Прерванный daily/weekly не сохраняет позицию и timestamp; следующий запуск начинается с нуля. Пропущенный weekly предложи отдельным обзором, не встраивай внутрь daily open.

## 5. Inbox debt

Большой Inbox не разбирай внутри weekly до конца. Предложи отдельную
triage-сессию с продуктовым ориентиром 15 минут; если пользователь сопротивляется,
предложи 10 или 5. Это настройка recovery-сессии, а не универсальная авторская
длительность triage или weekly. Сессия не завершает weekly автоматически.
Временное расписание triage создавай только после подтверждения; после очистки
долга предложи удалить его, но не удаляй молча.

## 6. Scheduler и status

Предлагай независимые host-native расписания `daily open`, `daily close` и `weekly`. Сначала спроси timezone/cadence/destination, покажи точный prompt и preview, затем создавай/изменяй только после явного подтверждения.

Scheduled prompt должен:

- только читать capabilities/counts/categories;
- не включать task/project titles или notes без отдельного opt-in;
- коротко пригласить открыть интерактивный review;
- всегда сообщить успех либо безопасную ошибку подключения;
- не менять SingularityApp, memory timestamps или другие schedules.

Если native scheduler недоступен, объясни ограничение без OS cron/launchd fallback.

`status` показывает MCP availability/нужные capabilities, IDs/modes выбранных roots, рабочие дни, наличие native scheduler и review timestamps. Не показывай названия/тексты задач/проектов, токены или raw diagnostic logs.
