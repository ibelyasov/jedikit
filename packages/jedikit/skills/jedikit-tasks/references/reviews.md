# Обзоры, память и расписание

Назначение: проводить daily/weekly с правильным охватом, управлять только минимальной native memory и безопасно предлагать host-native расписания.

## Разделы

1. Native memory
2. Daily open
3. Daily close
4. Weekly review
5. Inbox debt
6. Scheduler и status

## 1. Native memory

Автоматически храни только:

- timezone и рабочие дни;
- окна daily open/close и weekly;
- IDs root/`Общее` и режимы roots (`work / personal / always`);
- timestamp только полностью и явно завершённого daily close/weekly.

Не храни названия/тексты задач и проектов, raw capture, review history или checkpoint прерванного обзора. Используй только native memory хоста; файлового, Singularity metadata или скрытого fallback нет.

Timezone, рабочие дни и окна — операционные настройки, а не task content. Setup сохраняет их после общего preview; служебную задачу или setup memo в SingularityApp не создавай.

- `memory show`: показать allowlist выше; legacy task/project content не читать и не выводить.
- `memory forget`: уточнить одну настройку/ID/timestamp, показать preview ровно этого ключа и удалить только после подтверждения.
- `memory reset`: preview всех присутствующих разрешённых ключей без task/project content, подтверждение, затем последовательная очистка; при первой ошибке остановиться и показать applied/unapplied.

Если native memory недоступна, объясни это один раз за session и продолжай без восстановления/сохранения состояния.

## 2. Daily open

1. По timestamp проверь вчерашний daily close. Если он пропущен, автоматически проведи полный catch-up за вчера по правилам daily close до нового open; не переноси задачи молча.
2. Спроси ресурс: `низкий / обычный / высокий`. Не выводи его из числа задач.
3. Прочитай `task_list_today(timezone)`, `task_list_overdue(timezone)` и открытые задачи через пагинированный `task_list`; локально проверь все непустые `deadline`, включая будущие. Это намеренно широкое чтение: текущая схема `task_list` не даёт range-query или sparse `fields`, а задача с внешним deadline может не иметь `start`. Не включай removed/archived и recurrence instances, не передавай прочитанный content во внешнюю доставку и не считай прошедший start deadline.
4. Определи профиль дня по рабочим дням и пользовательскому выбору: work roots в рабочий день, personal roots в личный, `always` всегда. Для каждой задачи отдельно: задачу из противоположной области включай только при её собственном deadline сегодня или явном выборе пользователя; deadline одной задачи не включает остальные задачи области. Будущий deadline покажи отдельно и спроси, требует ли он действия сегодня.
5. Покажи **фокус-лист на сегодня** без числового лимита и обязательно скажи: «Календарь и доступное время не проверены».
6. После общего preview/подтверждения последовательно выставь выбранным задачам `start=today` и проверь результат.
7. Для исключённых уже-today задач предложи `оставить / снять start / новая дата`; решение и новая дата — только пользователя.

Не задавай фиксированные часы, не обещай вместимость и не меняй deadline.

## 3. Daily close

1. Покажи незавершённые today/overdue и спроси решение, не выполняя silent rollover.
2. Проверь только реальные проекты, затронутые сегодня: выведи их из текущего `task_list(modifiedSince=<начало локального дня>)` и проектов, явно названных в текущем диалоге. Не сохраняй `touched_project_ids` в memory. Затронутость означает, что задача создана, изменена, завершена, отменена или перемещена сегодня.
3. Контейнеры исключи. Для каждого затронутого проекта проверь результат и стартуемый шаг.
4. Если шага нет, показывай проекты по одному и спрашивай, хочет ли пользователь определить шаг. Не создавай его автоматически.
5. Отдельно предложи короткую проверку незакрытых мелких хвостов («гвоздодёр»), но не считай её заменой обзора.
6. Только после всех секций и явного «завершить» обнови timestamp.

## 4. Weekly review

Каждый запуск начинается с первого шага:

1. Inbox и состояние долга разбора.
2. Через `task_list` прочитай незавершённые и отменённые задачи и проверь их поля `start`/`deadline`, включая будущие внешние deadline; отдельно прочитай `task_list_overdue(timezone)`.
3. Все активные реальные проекты, не только затронутые сегодня.
4. Для каждого: наблюдаемый результат и один стартуемый ближайший шаг. Root/`Общее` исключить.
5. Предложить жизнеспособный недельный фокус без числовой квоты.
6. Сказать: «Календарь и доступное время не проверены».
7. После всех секций запросить явное завершение и только тогда обновить timestamp.

Прерванный daily/weekly не сохраняет позицию и timestamp; следующий запуск начинается с нуля. Пропущенный weekly предложи отдельным обзором, не встраивай внутрь daily open.

## 5. Inbox debt

Большой Inbox не разбирай внутри weekly до конца. Предложи отдельную triage-сессию: канонический старт 15 минут; при сопротивлении можно выбрать 10 или 5. Это не завершает weekly автоматически. Временное расписание triage создавай только после подтверждения; после очистки долга предложи удалить его, но не удаляй молча.

## 6. Scheduler и status

Предлагай независимые host-native расписания `daily open`, `daily close` и `weekly`. Сначала спроси timezone/cadence/destination, покажи точный prompt и preview, затем создавай/изменяй только после явного подтверждения.

Scheduled prompt должен:

- только читать capabilities/counts/categories;
- не включать task/project titles или notes без отдельного opt-in;
- коротко пригласить открыть интерактивный review;
- всегда сообщить успех либо безопасную ошибку подключения;
- не менять SingularityApp, memory timestamps или другие schedules.

Если native scheduler недоступен, объясни ограничение без OS cron/launchd fallback.

`status` показывает MCP availability/нужные capabilities, IDs/modes выбранных roots, рабочие дни, наличие native scheduler и review timestamps. Не показывай названия/тексты задач/проектов, токены или raw diagnostic logs.
