# Контракт разработки JediKit

JediKit содержит пять русскоязычных Agent Skill для Hermes Agent: `jedikit-tasks` для SingularityApp, `jedikit-habits` для Habitify и ритуалов, `jedikit-calendar` для Google Calendar, `jedikit-planning` для Плана дня и `jedikit` для навигации по запросу. Пользовательские инструкции, обсуждения, коммиты и PR пишем по-русски; identifiers, команды и API сохраняем оригинальными.

Правила разработки живут только в этом файле; `CLAUDE.md` и другие копии правил не создавай.

## Источники истины и карта репозитория

Перед изменением прочитай [CONTEXT.md](CONTEXT.md) и относящиеся к задаче [ADR](docs/adr/). CONTEXT задаёт термины и модель, ADR — принятые решения, `skills/` — действующие инструкции. Не переоткрывай принятые решения по собственной инициативе. Если два действующих решения противоречат друг другу, останови затронутую работу и сообщи владельцу с точными ссылками; рутинные детали решай самостоятельно.

| Путь | Назначение |
| --- | --- |
| `skills/jedikit-*/`, `skills/jedikit/` | Единственный источник инструкций и справочных материалов пяти скиллов |
| `skills/*/tools.json` | Машиночитаемый контракт инструментов провайдерных скиллов; у `jedikit-planning` и `jedikit` его нет |
| `plugin.json` | Portable manifest для `hermes plugins install` |
| `README.md` | Назначение, установка в Hermes и требования к нему |
| `CONTEXT.md`, `docs/adr/` | Единый словарь и решения |
| `research/` | Основания, контракты провайдеров и Hermes, реестр источников `research/sources.md` |
| `BACKLOG.md` | Отложенные возможности и явные исключения |
| `.github/workflows/check.yml` | Статические проверки в CI |
| `LICENSE`, `THIRD-PARTY-NOTICES.md` | MIT оригинальных материалов и права третьих лиц |
| `.work/` | Игнорируемые Git временные планы и результаты проверок |

Текущий контракт описывай в канонических документах, временный план — в `.work/`. Канонические документы описывают только то, что есть сейчас: без истории версий, «прежде/теперь» и дат принятия решений. Датированное provenance внешних источников остаётся в `research/`. Используй термины CONTEXT в предложениях, исследованиях и сценариях проверки.

Задачи проекта не ведутся в GitHub Issues: не создавай issues и не ссылайся на них из документов.

## Авторинг и границы

- В каждом `SKILL.md` обязателен YAML frontmatter с `name` (kebab-case, совпадает с каталогом) и `description` (когда выбирать скилл, без пересказа процедуры). Файл — не более 7000 байт UTF-8: это компактная точка входа, подробности живут в references. Основной текст даёт наблюдаемый результат; подробности выносятся в локальные `references/`.
- Один корневой `skills/` и portable `plugin.json`; без generated copies, вложенных пакетов и других manifests. Hermes подключает тот же `skills/` через `skills.external_dirs` или `hermes plugins install` ([ADR 0005](docs/adr/0005-hermes-plugin-host-connections.md)).
- Авторинг под Hermes: frontmatter только `name` и `description`, без `metadata.hermes` и других расширений — portable loader отбрасывает скилл с вложенным `metadata`. Frontmatter должен быть валидным YAML: значение `description` пиши в двойных кавычках, без неэкранированных `"` внутри. Portable loader Hermes отбрасывает скилл с невалидным frontmatter, а `validate` сообщает об этом только warning. Первые 57 символов `description` попадают в индекс скиллов и должны различать скилл. Файлы скилла читаются `skill_view(name="<скилл>", file_path="references/<file>.md")` или `file_path="tools.json"`: Markdown-ссылка файл не загружает, `../` запрещён, соседний скилл загружается по своему `name`.
- Скиллы устанавливаются отдельно: нужные правила пересказывают в своих `references/` и не ссылаются на `docs/`, `CONTEXT.md`, `research/` или файлы других скиллов, кроме обязательных `SKILL.md`, `references/write-policy.md`, `references/tools.md` и `tools.json` скилла-владельца. Какие досье лежат под каким скиллом, показывает [research/README.md](research/README.md). Другой скилл называют по имени; правила записи владельца читают перед операциями с его провайдером. Связи и явные передачи — по [ADR 0012](docs/adr/0012-skill-composition.md).
- Только инструкции, `plugin.json`, `tools.json` и документы. `tools.json` — декларативные данные, а не код. Не добавляй собственный код, скрипты, генераторы, MCP/proxy/runtime, MCP-декларации или инфраструктуру модельных проверок. Пробел в штатной проверке сообщай владельцу; новый код требует отдельного решения ([ADR 0004](docs/adr/0004-no-custom-code.md)).
- Подключения даёт Hermes. SingularityApp — официальный hosted MCP на сервере `singularity`; Habitify — операции хоста по бизнес-контракту REST/OpenAPI v2, с ключом только у доверенного адаптера хоста ([ADR 0001](docs/adr/0001-habitify-via-rest.md)); Google Calendar — инструменты сервера `google_calendar` ([ADR 0009](docs/adr/0009-separate-calendar-skill.md)). Официальный Habitify MCP не используется. Пакет не объявляет MCP и секреты. У владельца подключения, toolsets и cron настраивает clanwright.
- `skills/*/tools.json` (`version: 2`) у провайдерных скиллов задаёт у каждого инструмента сервер, базовое имя без префикса `mcp__<server>__` и `access: read | write`; у Habitify и Google Calendar ещё `required`. Habitify: чтения — сервер `habitify_read`, записи — `habitify`; Google Calendar — `google_calendar`. Имена — внешний контракт с Hermes: меняй их только вместе со скиллом и отмечай изменение в release notes. При нехватке инструментов скилл называет недостающие базовые имена и рекомендует подключить их в Hermes; сам ничего не устанавливает и не настраивает.
- Все блокирующие пробелы полей собираются одним вопросом `clarify` со свободным ответом; известное, необязательное и относительные даты не переспрашиваются. Глубокое уточнение намерения — через внешний скилл `grill-me` (`skills_list`, затем `skill_view`). Если он недоступен, назови его и рекомендуй установить в Hermes, без собственного интервью ([ADR 0013](docs/adr/0013-clarification.md)).
- Записи: полная явная команда, в том числе несколько названных записей на разных провайдерах, — сразу; одиночное предложение агента — одна строка и «да», собранный агентом набор — один общий Preview и подтверждение; согласие — карточка `clarify` «Да»/«Нет», timeout и пропуск не согласие. Безвозвратная потеря данных Habitify (удаление привычки, области, удаление/отмена отметок) всегда требует однострочного подтверждения. Однозначное удаление События — сразу; в отчёте укажи 30 дней в корзине Google и восстановление только в интерфейсе. Группа — последовательно, стоп на первой ошибке, отчёт applied/unverified/unapplied, без автоматического отката; после каждой записи Read-back ([ADR 0014](docs/adr/0014-confirmations.md)). Фоновые запуски только читают ([ADR 0003](docs/adr/0003-no-unattended-writes.md)).
- Hermes `memory` хранит только настройки ([ADR 0006](docs/adr/0006-memory-holds-settings-only.md)). Kanban исключён ([ADR 0007](docs/adr/0007-no-kanban.md)). После переноса идеи, справки или встречи команда «перенёс, отмени» отменяет исходный Inbox item через `task_cancel` сразу; одно «перенёс» вызывает предложение отменить. При передаче встречи `jedikit-calendar` отмена возможна только после успешного создания и Read-back События ([ADR 0008](docs/adr/0008-cancel-instead-of-delete.md)). Off Mode отсутствует в API Habitify: только инструкция для приложения, команды `off` нет.
- Сохраняй чужие изменения. Не включай в файлы или логи секреты и личные данные провайдеров. Provider, DNS, ACME, deploy, backup-writer, restore, prune, credential и secret mutations требуют явного разрешения владельца.

## Проверки и доказательства

Штатные проверки из корня, без аккаунтов провайдеров:

```sh
hermes plugins validate . --json
hermes plugins doctor . --ci
git diff --check "$(git hash-object -t tree /dev/null)" HEAD  # всё дерево HEAD, как в CI
git diff --check HEAD                                         # незакоммиченные правки
```

- Hermes validate включает security scanner, doctor проверяет discovery/load/registration. Exit `0` сам по себе не доказывает точный inventory пяти скиллов или отсутствие component diagnostics: читай reports и warnings. Оба проверяют `skills/` как portable plugin; отдельного валидатора для подключения через `skills.external_dirs` нет.
- Не заменяй недостающие проверки Python helper или собственной assertion logic.
- CI использует официальные инструменты с версиями и SHA из `.github/workflows/check.yml`, без моделей и provider accounts. Hermes Action закреплён на commit с исправлением установки; при выходе Hermes release с этим исправлением переведи pin на release tag. Action не экспортирует CLI, поэтому `doctor` выполняется локально.
- У scanner Hermes нет ignore для `.work/`: локальный scan читает и её, а чистый checkout в CI её не содержит. Не удаляй логи ради зелёного verdict; отделяй warnings рабочего каталога от проверки поставляемого Git tree.

Проверка изменений — штатные валидаторы, `git diff --check` и независимое ревью агентом. Модельных прогонов нет. Сохраняй читаемый вывод каждой проверки, команду, exit status и длительность в `.work/`. Отчёт завершения: изменённые пути, выполненные проверки и ссылки на вывод, непроверенные слои и риски. Статика, загрузка, поведение модели, авторизация провайдеров и запись/Read-back — разные результаты. Владелец пользуется скиллами и сообщает о проблемах; обязательного ручного runtime-гейта нет. Публикация версии (тег и GitHub release) — отдельное решение владельца.

## Исследования

Для вопросов о синтаксисе, настройке, версиях и поведении CLI/API сначала проверь установленную версию, локальную справку/source и `research/`; затем текущую официальную документацию или официальный `llms.txt`. Для обычного редактирования документов внешний поиск не нужен.

Каждый проверяемый тезис сопровождай первичной ссылкой и датой доступа; для реализации сохраняй version/commit pin. Различай заявления vendor, независимое чтение source, локально выполненную проверку и anecdote. Недоступный источник и непроверенный runtime явно оставляй неопределёнными. Авторские положения Дорофеева отделяй от академических выводов и продуктовых решений; расхождение с автором выноси владельцу. Сохраняй provenance в `research/sources.md`, формулируй самостоятельно, не копируй книги и чужие ассеты. Правовые основания — `research/legal-and-attribution.md`.
