# Цвет записи календаря задаёт смысл занятия

Каждая запись JediKit в календаре — Событие, Бронь, Распорядок — получает `colorId` по одной оси: смыслу занятия. Категорий цвета девять, цвета сгруппированы семействами, чтобы лента дня читалась без легенды: синие — люди, жёлто-оранжевые — голова, зелёно-бирюзовые — энергия, фиолетовый — База, серый — Рутина.

| Категория | Что входит | `colorId` |
| --- | --- | --- |
| Встречи | Договорённости с людьми по делу, в том числе рабочие созвоны | `9` Blueberry |
| Общение | Друзья, близкие, свидания, семья | `1` Lavender |
| Работа и фокус | Работа, свои проекты, планирование, рефлексия | `5` Banana |
| Обучение | Любое обучение, в том числе по работе | `6` Tangerine |
| Заряд | Спорт, хобби — активное и наполняющее | `10` Basil |
| Досуг | Сериал, игры, кино — развлечение без усилия | `7` Peacock |
| Покой | Сон, отдых, духовная практика | `2` Sage |
| База | Врач, анализы, финансы, налоги, документы, госуслуги | `3` Grape |
| Рутина | Дорога, еда, быт, покупки — всё остальное | `8` Graphite |

`11` Tomato и `4` Flamingo не используются. Категория определяется порядком вопросов, срабатывает первый подходящий: Покой → Обучение → База → Встречи → Общение → Работа и фокус → Заряд → Досуг → Рутина. Явно названная пользователем категория или цвет сильнее порядка. Бронь красится по содержанию Задачи, Распорядок — по тому, что даёт действие или ритуал; своего цвета у роли нет, роль читается только по метке в описании.

Транспорт — поле `colorId` у `create-event` и `update-event` сервера `@cocal/google-calendar-mcp` 2.7.0; `colorId` входит в допустимые `fields` чтения. Это подтверждено чтением source, живыми вызовами не проверено ([досье Google Calendar](../../research/providers/google-calendar.md)). Цвет события — личное оформление: гости его не видят, видят пользователи с правом изменять календарь.

## Considered Options

- Цвет по роли JediKit (Событие, Бронь, Распорядок): роль уже видна по метке, а лента из трёх цветов не говорит, чем занят день.
- Цвет по субъективной нагрузке: требует оценки при каждой записи и меняется вместе с состоянием человека, поэтому цвет нельзя назначить без вопроса.
- Отдельный календарь на категорию: множит календари чтения и записи и ломает модель одного календаря записи ([ADR 0009](0009-separate-calendar-skill.md)).
- Именованные labels Google (`eventLabelId`, `Calendars.labelProperties.eventLabels`): дают легенду в интерфейсе, но выбранный MCP их не предоставляет; отложены в [BACKLOG](../../BACKLOG.md).
- Готовые классификации времени ICATUS 2016 и колесо баланса: использованы как призмы для поиска пропущенных сфер, а не как список категорий. ICATUS делит время для статистики (оплачиваемый и домашний труд, уход, учёба, общение, досуг, забота о себе) и не отличает встречу от работы в одиночку; колесо баланса описывает сферы жизни, а не занятия на ленте дня.

## Consequences

Цвет не спрашивается и не блокирует запись: это не блокирующий пробел по [ADR 0013](0013-clarification.md). Исключение — цвет, названный словами: если категория по порядку вопросов входит в названное семейство или цвет, она берётся без вопроса, явно названный цвет вне схемы используется как назван, иначе выбор входит в общий `clarify` запроса. Схема фиксирована в скилле и не хранится в памяти ([ADR 0006](0006-memory-holds-settings-only.md)). Направление одно — от смысла к цвету: ни роль, ни категорию существующей записи цвет не доказывает.

Существующие записи перекрашиваются только по явной просьбе. Одиночная явная команда выполняется сразу; перекраска набора, собранного агентом, — по [ADR 0014](0014-confirmations.md): один Preview и подтверждение. Записи с уже заданным `colorId` массовая перекраска не трогает, если пользователь явно не попросил перекрасить и их. Сервер не читает `eventLabelId`, поэтому запись без `colorId` может быть окрашена вручную label Google, а взаимодействие `colorId` с label не проверено: Preview говорит об этом прямо. Ограничения update — те же, что у других изменений. При переносе, переименовании и других изменениях `colorId` не передаётся. Read-back сверяет `colorId` через `get-event` и подтверждает конфигурацию, а не вид в интерфейсе. Правила лежат в `references/tools.md` скилла `jedikit-calendar`; `jedikit-planning` применяет их к Броням.
